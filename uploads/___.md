# 버츄얼 스레드란

> 발표 원고 · 이름 규칙: **요청 A / 가상 스레드 Q(대문자) / 실제 스레드 q(소문자)**

---

## 슬라이드 1 — 문제 제기

지난 발표에서 다룬 것처럼, 기존 방식은 요청 하나가 오면 플랫폼 스레드 하나가 할당되어 응답이 나갈 때까지 모든 과정을 담당합니다.

여기서 문제가 생깁니다. LLM을 호출하는데 응답이 10분 걸린다면, 그 요청을 맡은 스레드는 10분 내내 그 요청에 묶여 있습니다. 이런 요청이 스레드 최대 개수만큼 들어오면 **서버는 더 이상 요청을 받지 못합니다.**

멈춘 게 아니라 놀고 있는데도 못 받는 겁니다. 스레드들은 전부 "기다리는 중"이지 "일하는 중"이 아니니까요.

오늘은 버츄얼 스레드가 이 상황을 어떻게 해결하는지, 그리고 실제로 어떻게 동작하는지 이야기하겠습니다.

---

## 슬라이드 2 — 용어 정리

먼저 네 가지 용어를 정리하고 가겠습니다. 이름이 비슷해서 헷갈리기 쉬운데, **셋은 사실상 같은 것이고 하나만 다릅니다.**

```
┌─────────────────────────────────┐   ┌──────────────────────┐
│  실제 실행하는 쪽 — 셋은 같은 실체  │   │    정보를 담는 쪽      │
│                                 │   │                      │
│  ┌───────────────────────────┐  │   │  ┌────────────────┐  │
│  │ 커널 스레드                │  │   │  │ 가상 스레드     │  │
│  │ OS가 관리하는 진짜 실행 자원 │  │   │  │ 실행할 작업과   │  │
│  └───────────────────────────┘  │   │  │ 진행 상태를     │  │
│  ┌───────────────────────────┐  │   │  │ 담은 객체       │  │
│  │ 플랫폼 스레드              │  │   │  └────────────────┘  │
│  │ 커널 스레드의 자바 표현, 1:1│  │   │                      │
│  └───────────────────────────┘  │   │  · OS는 존재를 모름    │
│  ┌───────────────────────────┐  │   │  · 혼자서는 실행 불가   │
│  │ 캐리어 스레드              │  │   │  · 캐리어에 올라타야    │
│  │ 가상 스레드를 태우는 중인 상태│  │   │    동작              │
│  └───────────────────────────┘  │   │                      │
└─────────────────────────────────┘   └──────────────────────┘

      가상 스레드는 캐리어 스레드에 올라타야만 실행된다
```

**스레드** — 보통 우리가 말하는 스레드는 OS 커널 스레드입니다. 실제로 CPU 자원을 배정받는 진짜 실행 단위죠.

**플랫폼 스레드** — 자바에서 쓰는 스레드입니다. 커널 스레드와 1:1로 대응하기 때문에, 이름만 나눈 것이지 실체는 커널 스레드라고 봐도 됩니다.

**캐리어 스레드** — 플랫폼 스레드인데, 지금 가상 스레드를 태우고 있는 상태를 부르는 말입니다. 별도의 종류가 아니라 **역할 이름**입니다.

**가상 스레드** — 이것만 성격이 다릅니다. 실행 능력이 없고, 힙에 놓인 자바 객체입니다.

여기서 강조하고 싶은 건 왼쪽 셋은 사실상 같은 것이고, **오른쪽 하나만 다른 종류**라는 점입니다.

> 참고로 이런 문장이 성립합니다.
> - 모든 캐리어 스레드는 플랫폼 스레드다 → **참**
> - 모든 플랫폼 스레드는 캐리어 스레드다 → **거짓** (`main` 스레드는 캐리어가 아님)

## 슬라이드 3 — 기존 방식의 흐름

우리가 대부분 쓰는 스레드 기반 Spring을 보겠습니다.

```
A요청 → 과정1 → 과정2 → … → A응답
```

요청 A에 스레드 `q`가 할당됩니다. 이 `q`는 자바에서 쓰는 스레드니까 플랫폼 스레드이고, 동시에 실제 커널 스레드이기도 합니다.

문제는 여기입니다. **과정에서 시간이 얼마나 걸리든, 대기를 하든, `q`는 응답이 나갈 때까지 계속 점유됩니다.** 과정2가 10분 대기해야 한다면 `q`도 10분 이상 묶여 있습니다.

## 슬라이드 4 — 버츄얼 스레드의 흐름

같은 요청을 버츄얼 스레드 관점에서 보겠습니다.

요청 A에 먼저 **가상 스레드 Q를 할당합니다.** Q는 해야 할 일을 정의한 채 큐에 들어갑니다.

스케줄러가 놀고 있는 캐리어 스레드 `q`를 골라 **Q를 `q` 위에 마운트합니다.** 이제 실제로 `q`가 일을 진행합니다.

과정2에서 대기가 발생하면 **Q는 여태 진행한 정보를 힙에 저장하고 `q`를 반납합니다.** 이 순간부터 `q`는 자유입니다.

응답이 오면 Q는 다시 캐리어 스레드를 할당받습니다. 이때 캐리어는 `q`일 수도, 다른 스레드일 수도 있습니다.

### 10분 대기 상황 비교

```
[ 기존 방식 ]
스레드 q1   ██ ┈┈┈┈┈┈ 과정2 — 10분 대기, 점유 중 ┈┈┈┈┈┈ ███
스레드 q2   ██ ┈┈┈┈┈┈ 과정2 — 10분 대기, 점유 중 ┈┈┈┈┈┈ ███
새 요청     ▓▓▓▓▓▓▓▓ 남은 스레드 없음 — 요청 거절 ▓▓▓▓▓▓▓▓

[ 버츄얼 스레드 ]
가상 스레드 Q  ██ ┈┈┈┈ 과정2 — 10분 대기, 힙에 저장 ┈┈┈┈ ███
캐리어 스레드 q ██ ▒▒ ▒▒ ▒▒ ▒▒ ▒▒ ▒▒ ▒▒ ▒▒ ███
                    ↑ 같은 10분 동안 q가 처리한 다른 요청들
```

요청 하나의 처리 시간은 여전히 10분입니다. 달라진 건 **그 10분 동안 서버가 마비되느냐, 다른 요청을 계속 받느냐**입니다.

## 슬라이드 5 — 왜 다른 스레드가 이어받아도 되는가

여기서 의문이 생길 수 있습니다. **"다른 스레드가 할당되면 안 되지 않나?"**

가상 스레드의 역할을 정의하면 답이 나옵니다.

> **가상 스레드는 실행할 작업과 지금까지의 진행 상황, 모든 메타데이터를 저장한 자바 객체입니다.**
> **캐리어 스레드는 그것을 읽어서 실제로 동작시키는 스레드입니다.**

정보가 전부 가상 스레드 쪽에 있으니, 실행자는 누구든 상관없습니다. 캐리어는 아무 정보도 갖고 있지 않은 빈 껍데기니까요.

우리가 자주 쓰는 AI로 비유하면 이렇습니다. **A 세션에서 작업하다가 진행 상황을 `.md` 파일로 정리해두면, 다른 세션에서 그 파일을 읽고 이어서 작업할 수 있습니다.** 가상 스레드가 그 `.md` 파일 역할을 합니다.

기존 방식이 스레드를 놓아줄 수 **없었던** 이유도 여기서 설명됩니다.

```
기존:  정보가 스레드에 박힘  →  스레드를 놓으면 정보도 잃음  →  못 놓음
가상:  정보를 힙으로 분리    →  스레드를 놓아도 정보는 남음  →  놓을 수 있음
```

## 슬라이드 6 — 구조적으로 본 전체 흐름

가상 스레드는 세 장소를 돌아다닙니다.

```
        마운트                     언마운트
┌──────────────┐  →  ┌──────────────┐  →  ┌──────────────┐
│ ① 스케줄러 큐  │     │ ② 캐리어 스레드│     │ ③ 힙          │
│ 실행 순서 대기 │     │ 실제로 실행 중 │     │ 스택 저장, 잠듦│
│ 아직 실행 전  │     │ OS 스레드 점유 │     │ OS 스레드 안 씀│
└──────────────┘     └──────────────┘     └──────────────┘
       ↑                                          │
       └──────────────────────────────────────────┘
            응답 도착 → 언파크 → 큐에 다시 등록
```

전체 순서를 한 줄로 쓰면 이렇습니다.

> Q 생성 → 큐에 등록 → 캐리어가 꺼냄 → 마운트 → 실행 → 대기 발생 → 언마운트 → 큐에서 빠짐, 힙에 방치 → 응답 도착 → 큐에 다시 등록(언파크) → 캐리어가 꺼냄 → 마운트 → 이어서 실행

한 가지만 짚으면, **대기 중인 가상 스레드는 큐에 있지 않습니다.** 큐에 있으면 캐리어가 계속 꺼내서 "아직이야?" 하고 확인해야 하니까요. 응답이 도착해야 비로소 큐로 돌아옵니다. 이걸 언파크라고 부릅니다.

## 슬라이드 7 — FastAPI 이벤트 루프와의 차이

그렇다면 FastAPI의 이벤트 루프와는 무엇이 다를까요.

### 먼저 같은 점

사실 밑바닥 원리는 거의 같습니다. 둘 다 "기다릴 때는 상태만 저장하고 실제 스레드를 놓아준다"는 동일한 아이디어입니다. 용어만 다릅니다.

| 자바 | 파이썬 |
|---|---|
| 가상 스레드 | 코루틴 |
| 캐리어 스레드 | 이벤트 루프 스레드 |
| 언마운트 | `await`에서 양보 |
| 스케줄러 큐 | 이벤트 루프 태스크 큐 |

### 구조 비교

```
[ FastAPI — asyncio ]          [ 자바 — 가상 스레드 ]
 ○ ○ ○ ○ ○ ○  코루틴들           ○ ○ ○ ○ ○ ○  가상 스레드들
 ○ ○ ○ ○ ○ ○                    ○ ○ ○ ○ ○ ○
       ↓                          ↓         ↓
┌──────────────┐            ┌─────────┐ ┌─────────┐
│ 이벤트 루프 1개 │            │ 캐리어   │ │ 캐리어   │
└──────────────┘            └─────────┘ └─────────┘

 코어를 쓰려면 프로세스 복제      코어 수만큼 병렬 실행
 await로 양보 지점 명시          명시 없이 동기 코드 그대로
```

### 차이 1 — 개발자가 명시해야 하느냐

FastAPI는 `async def`로 선언하고 `await`를 직접 찍어줘야 합니다. 어디서 양보할지를 개발자가 알려주는 방식이죠.

자바는 표시가 없습니다. 평범한 동기 코드를 쓰면 JDK가 블로킹 지점을 알아서 잡아냅니다.

```python
user = await repo.find(id)      # 양보한다고 내가 선언
```

```java
var user = repo.findById(id);   // 표시 없음. 알아서 언마운트
```

이 차이 때문에 파이썬에는 **함수 색깔 문제**가 생깁니다. `async` 함수를 부르려면 호출하는 쪽도 `async`여야 해서, 한 곳에 도입하면 호출 체인 전체가 전염됩니다. 라이브러리도 `httpx`, `asyncpg` 같은 async 전용 버전이 따로 필요하고요. 자바는 이 문제가 없어서 기존 코드와 라이브러리를 그대로 씁니다.

### 차이 2 — 루프가 몇 개냐

asyncio는 프로세스당 이벤트 루프가 하나입니다. 코루틴이 수천 개여도 실제로는 한 번에 하나씩만 실행되죠. 그래서 코어를 다 쓰려면 `uvicorn --workers 8`처럼 **프로세스를 복제**합니다. 워커마다 인터프리터가 통째로 복사되니 메모리 부담이 있습니다.

자바는 캐리어 스레드가 코어 수만큼 있어서 **하나의 프로세스 안에서 진짜로 병렬 실행**됩니다. 힙도 하나를 공유하고요.

**실수했을 때의 대가도 다릅니다.** `async def` 안에서 실수로 동기 라이브러리를 부르면 루프가 하나뿐이라 **그 프로세스 전체가 멈춥니다.** 자바에서 피닝이 발생하면 캐리어 하나가 묶이지만, 나머지 캐리어는 살아 있습니다.

### 정리

| | FastAPI (async) | 자바 가상 스레드 |
|---|---|---|
| 밑바닥 원리 | 상태 저장 후 양보 | **동일** |
| 양보 지점 | `await`로 명시 | 자동 |
| 기존 코드 재사용 | async 버전 필요 | **그대로 사용** |
| 병렬 실행 | 프로세스 복제 필요 | 캐리어가 코어 수만큼 |
| 대표 함정 | 동기 라이브러리 호출 | `synchronized` 피닝 |
| 함정의 대가 | 프로세스 전체 정지 | 캐리어 1개 묶임 |

> **FastAPI는 "비동기를 쓰려면 코드를 비동기로 바꾸라"고 하고, 가상 스레드는 "동기 코드 그대로 두면 우리가 알아서 돌려주겠다"고 합니다.**

## 슬라이드 8 — 적용과 주의점

Spring Boot 3.2 이상이라면 설정 한 줄이면 됩니다.

```yaml
spring:
  threads:
    virtual:
      enabled: true
```

코드는 그대로 둡니다.

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> {
        var user   = repo.findById(id);      // 여기서 언마운트
        var answer = llmClient.ask(user);    // 10분 대기 → 언마운트
        return render(user, answer);         // 깨어나서 이어서 실행
    });
}
```

다만 세 가지는 짚고 가야 합니다.

**풀링하지 마세요.** 가상 스레드는 생성 비용이 거의 없습니다. 풀에 담아 재사용하면 개수 제한이 다시 생겨 이점이 사라집니다.

**CPU 작업엔 효과가 없습니다.** 이득은 오직 기다리는 시간에서 나옵니다.

**피닝을 조심하세요.** `synchronized` 블록 안에서 블로킹되면 언마운트하지 못하고 캐리어가 묶입니다. 캐리어는 몇 개 안 되니 오히려 더 심하게 막힐 수 있습니다. Java 24(JEP 491)부터 대부분 해결됐고, 그 이전 버전이라면 `ReentrantLock`으로 바꿔야 합니다.

```
-Djdk.tracePinnedThreads=full
```

이 옵션으로 피닝 발생 지점의 스택 트레이스를 확인할 수 있습니다.

> 덧붙여, 스레드가 아무리 늘어도 DB 커넥션 풀이 20개면 거기서 막힙니다. 주변 병목도 함께 봐야 합니다.

## 슬라이드 9 — 마무리

전체를 다섯 문장으로 잇겠습니다.

> 요청은 대부분의 시간을 기다리는 데 씁니다.
> **→** 그런데 기존 스레드는 기다리는 동안에도 비싼 OS 스레드를 붙잡습니다.
> **→** 기다릴 땐 진행 상황만 저장하고 자리를 비켜주면 됩니다.
> **→** 그러려면 스택을 저장하고 복원할 수 있어야 하고, 그게 Continuation입니다.
> **→** 그걸 스레드처럼 쓰게 감싼 것이 가상 스레드입니다.

그리고 마지막 한 줄입니다.

> **비동기의 성능을, 동기 코드의 가독성으로.**

## 부록 — 예상 질문과 답변

**Q. 요청이 더 빨라지나요?**
아니요. 요청 1건의 처리 시간은 그대로입니다. 3초 걸리던 건 여전히 3초입니다. 달라지는 건 **동시에 받을 수 있는 요청 수**입니다.

**Q. 요청이 여러 스레드로 쪼개져서 처리되나요?**
아닙니다. 요청 하나는 가상 스레드 하나가 처음부터 끝까지 순서대로 처리합니다. 나눠지는 건 요청이 아니라 **캐리어 스레드의 시간**입니다.

**Q. `ThreadLocal`은 깨지지 않나요?**
`ThreadLocal`은 캐리어가 아니라 가상 스레드에 소속되어 있어서 함께 이동합니다. MDC 로깅도 안전합니다. 다만 가상 스레드가 수십만 개면 `ThreadLocal`도 그만큼 생겨 메모리 부담이 커집니다. 대안은 `ScopedValue`입니다.

**Q. WebFlux는 이제 필요 없나요?**
단순히 동시 처리량이 부족했던 경우라면 가상 스레드로 충분합니다. 다만 백프레셔가 필요한 스트리밍, SSE·WebSocket 같은 지속 연결처럼 **리액티브 스트림의 의미론 자체가 필요한 경우**에는 여전히 WebFlux가 맞습니다.

**Q. WebFlux와 뭐가 다른가요?**
WebFlux는 아키텍처를 바꿔서 문제를 풀었고, 가상 스레드는 아키텍처를 안 바꾸고 풀었습니다.

| | Spring MVC | 가상 스레드 | WebFlux |
|---|---|---|---|
| 서버 | 톰캣 | 톰캣 | 네티 |
| 코드 | 절차적 | 절차적 | 리액티브 |
| 스레드 묶임 | 있음 | 없음 | 없음 |
| 전환 비용 | — | 설정 한 줄 | 전면 재작성 |
