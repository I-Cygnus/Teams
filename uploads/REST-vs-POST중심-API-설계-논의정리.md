## 1. REST란 무엇인가

REST는 **RE**presentational **S**tate **T**ransfer의 약자다. 2000년에 Roy Fielding이 박사 논문에서 처음 정의했다.

핵심은 **REST가 특정 기술이나 프로토콜이 아니라 "설계 철학(아키텍처 스타일)"**이라는 점이다. "좋은 건물을 짓는 원칙"에 비유할 수 있다 — 벽돌을 쓰라는 구체적 지시가 아니라 "채광이 잘 되게 하라" 같은 원칙 모음이다.

Fielding은 사실 웹(HTTP)이 왜 이렇게 잘 굴러가는지를 관찰하고, 그 성공 비결을 이론으로 정리한 것이다.

---

## 2. REST의 6가지 원칙과 HATEOAS

Fielding이 말한 REST의 제약조건:

- **클라이언트-서버 분리**: 화면(클라이언트)과 데이터 처리(서버)를 분리한다.
- **무상태(Stateless)**: 서버가 이전 요청을 기억하지 않는다. 매 요청이 필요한 정보를 스스로 다 담아야 한다.
- **캐시 가능(Cacheable)**: 응답을 저장해뒀다 재사용할 수 있어야 한다.
- **계층화**: 중간에 로드밸런서, 프록시가 껴 있어도 클라이언트는 몰라도 된다.
- **주문형 코드(선택사항)**: 서버가 클라이언트에 실행 코드를 보낼 수도 있다.
- **일관된 인터페이스(Uniform Interface)**: REST의 핵심이자 대부분이 놓치는 부분.

"일관된 인터페이스" 안에 **HATEOAS**(Hypermedia As The Engine Of Application State)가 있다. "응답 안에 다음에 뭘 할 수 있는지 링크를 같이 넣어줘야 한다"는 뜻이다. 웹사이트에서 URL을 외워서 다니지 않고 페이지의 링크를 눌러가며 탐색하듯, API도 스스로 길을 안내해야 진짜 REST라는 것이다.

---

## 3. "REST API"와 "RESTful"은 같은 것인가

단어 자체로는 거의 같은 뜻이다. "RESTful하다"는 "REST 원칙을 잘 따른다"는 형용사일 뿐이다. 일상에서는 구분 없이 써도 된다.

**그러나 여기서 유명한 논쟁이 시작된다.** 흔히 "REST API"라 부르는 것 대부분이 Fielding의 엄격한 기준으로 보면 사실 진짜 REST가 아니다. 특히 HATEOAS를 거의 아무도 안 지킨다.

### 리처드슨 성숙도 모델 (Richardson Maturity Model)

| 레벨 | 내용 |
|---|---|
| **레벨 0** | HTTP를 그냥 통로로만 씀 (사실상 옛날 방식 RPC) |
| **레벨 1** | URL로 자원을 구분하기 시작 (`/users/1`) |
| **레벨 2** | GET, POST, PUT, DELETE 같은 HTTP 메서드를 제대로 씀 ← **세상의 "REST API" 대부분이 여기** |
| **레벨 3** | HATEOAS까지 지킴 ← **Fielding이 말한 진짜 REST** |

즉 "REST API"라 부르는 것의 90% 이상은 레벨 2에 머물러 있고, 정통 REST는 현실에서 보기 드물다.

---

## 4. 요즘의 견해들

1. **순수주의(Fielding 본인)**: 2008년 블로그에서 "HATEOAS 없으면 REST라고 부르지 마라"고 강하게 못박음.
2. **"그냥 HTTP API/Web API라고 부르자"**: 정직하게 REST라는 말을 붙이지 말자는 흐름. 힘을 얻는 중.
3. **실용주의(다수)**: "이름이 중요한가? 일관되고 예측 가능하고 잘 작동하면 됐지." HATEOAS는 비용 대비 실익이 애매해 대다수가 "레벨 2면 충분"이라 타협.
4. **대안 기술의 부상**: GraphQL, gRPC, tRPC 등. 다만 REST가 죽은 것은 아니며 여전히 가장 널리 쓰이는 표준.

## 5. HATEOAS는 실제로 어떻게 생겼나

**HATEOAS가 없는 일반 응답:**

```json
{
  "orderId": 1001,
  "status": "pending",
  "total": 50000
}
```

클라이언트는 "결제하려면 어디로? 취소는? URL을 문서 보고 외워서 만들어야 하네"라고 고민하게 된다.

**HATEOAS가 적용된 응답:**

```json
{
  "orderId": 1001,
  "status": "pending",
  "total": 50000,
  "_links": {
    "self":   { "href": "/orders/1001" },
    "pay":    { "href": "/orders/1001/payment", "method": "POST" },
    "cancel": { "href": "/orders/1001/cancel",  "method": "POST" }
  }
}
```

핵심은 **응답 안에 "다음 행동과 그 주소"가 같이 들어있다**는 것. 그리고 **상태가 바뀌면 링크도 바뀐다.** 결제 완료(`paid`) 상태가 되면:

```json
{
  "orderId": 1001,
  "status": "paid",
  "_links": {
    "self":   { "href": "/orders/1001" },
    "refund": { "href": "/orders/1001/refund", "method": "POST" }
  }
}
```

`pay`가 사라지고 `refund`가 생긴다. 웹사이트에서 "결제하기" 버튼이 결제 후 사라지고 "환불하기"가 뜨는 것과 같은 원리다.

**왜 아무도 안 쓰나?** 클라이언트가 이 링크를 활용하려면 결국 "pay 링크가 오면 결제 버튼을 보여준다"처럼 링크 이름을 하드코딩하게 된다. 그러면 "URL을 하드코딩하나 링크 이름을 하드코딩하나 결합도는 비슷한데 서버만 복잡해진다"는 비판이 나온다. 이상은 아름답지만 실익이 애매하다는 게 중론.

## 6. REST vs GraphQL

가장 큰 차이는 **"누가 응답의 모양을 결정하느냐"**다.

- **REST**: 서버가 정한다. `/users/1`을 부르면 서버가 정해둔 유저 정보가 통째로 온다.
- **GraphQL**: 클라이언트가 정한다. "이름과 이메일만 줘"라고 요청하면 딱 그것만 온다.

### REST의 두 고질병

- **오버페칭(over-fetching)**: 이름 하나만 필요한데 주소, 전화번호, 가입일까지 전부 받음.
- **언더페칭(under-fetching) / N+1 문제**: 화면 하나 그리려고 요청을 여러 번 해야 함.

```
GET /users/1              → 유저 정보
GET /users/1/orders       → 주문 목록
GET /orders/1001/items    → 각 주문의 상품 (주문 개수만큼 반복)
```

**GraphQL은 한 번의 요청으로 해결:**

```graphql
query {
  user(id: 1) {
    name
    orders {
      id
      items { productName price }
    }
  }
}
```

### 트레이드오프

| 항목 | REST | GraphQL |
|---|---|---|
| 응답 모양 결정 | 서버 | 클라이언트 |
| 캐싱 | URL 단위라 쉬움 (HTTP 캐시, CDN) | 대부분 `POST /graphql` 하나로 가서 어려움 |
| 서버 부하/보안 | 상대적으로 단순 | 쿼리 깊이 제한 등 필요, 까다로움 |
| 학습·구축 비용 | 낮음 | 높음 |

> 흥미롭게도 GraphQL이 모든 요청을 `POST /graphql` 하나로 보내는 것은, 이 대화에서 논의된 "POST 위주" 방식과 정확히 같은 구조다.

복잡한 앱(모바일, 대시보드)엔 GraphQL이, 단순·캐싱 중요·공개 API엔 REST가 편하다.

## 7. "POST 위주로, URL에 목적을 담자"는 관점

**사용자의 입장:** HTTP 메서드 활용은 오히려 헷갈릴 수 있으므로, URL 자체에 목적을 담고 POST 위주로 쓴다. 확실한 조회는 GET을 함께 쓴다.

### 이것은 RESTful인가?

엄밀히 "RESTful" 라벨을 붙이려면 메서드를 규칙대로 써야 한다(레벨 2). 따라서 `POST /orders/1001/cancel` 방식은 정의상 RESTful이 아니라 **RPC 스타일**에 가깝다.

**그러나 그것이 나쁜 것은 아니다.** 이 방식을 지지하는 근거:

1. **메서드가 헷갈린다는 것은 진짜 문제다.** PUT vs PATCH(전체 교체 vs 부분 수정)의 차이, "결제·이메일 발송" 같은 명백한 동사형 행위를 억지로 명사+메서드로 우겨넣는 어색함은 REST의 오래된 약점이다.
2. **URL만 봐도 뭘 하는지 명확하다.** `POST /orders/1001/cancel`은 주석이 필요 없다. `DELETE /orders/1001`은 "취소야, 삭제야?" 헷갈린다.
3. **일관성이 곧 단순함이다.** 모든 게 POST면 클라이언트 코드가 단순해지고 "PUT이야 PATCH야" 논쟁이 사라진다. GraphQL도, gRPC도 사실상 POST 기반이다.

### REST 진영이 그래도 메서드를 고집하는 이유

HTTP 메서드에 부여된 **"약속된 성질"** 때문이다:

- **GET** = 안전(safe): 여러 번 불러도 안 바뀐다 → 캐시·CDN이 마음 놓고 최적화.
- **PUT/DELETE** = 멱등(idempotent): 두 번 보내도 결과 같다 → 재시도에 안전.
- **POST** = 이 약속이 없음: "결제"처럼 두 번 실행되면 안 되는 것에 어울림.

메서드를 규칙대로 쓰면 **HTTP 생태계(캐시, 프록시, 모니터링, 로드밸런서)가 API 의도를 자동으로 이해하고 최적화**해준다. 전부 POST로 통일하면 이 공짜 혜택을 포기하는 셈이며, 특히 조회를 POST로 하면 캐싱을 잃는다.

### 절충안

**조회는 GET, 나머지 변경 동작은 URL에 목적을 담아 POST.**

- 캐싱이 중요한 조회에선 HTTP의 공짜 혜택을 챙기고,
- 헷갈리는 PUT/PATCH/DELETE 논쟁은 피하며,
- 복잡한 비즈니스 동작은 `POST /orders/1001/cancel`처럼 명확하게 표현.

정직하게는 "REST"가 아니라 **"REST 스타일을 섞은 HTTP/RPC API"**다. 단, POST 위주로 갈 때 **멱등성 문제**(같은 요청이 두 번 가서 주문이 두 개 생기는 사고)는 스스로 챙겨야 한다. 보통 **멱등성 키(idempotency key)**로 해결한다.

## 8. 이런 방식을 부르는 명칭이 있는가

딱 떨어지는 공식 명칭은 없다. 여러 이름이 부분적으로 걸쳐 있다.

### 후보 1: RPC 스타일 (가장 정확한 상위 개념)
`POST /orders/1001/cancel`은 사실상 `cancelOrder(1001)`을 네트워크 너머로 부르는 것. JSON-RPC, gRPC, Twirp가 정식 구현체.
**반박:** 순수 RPC는 URL 하나(`/rpc`)에 몰아넣고 본문으로 함수를 구분한다. 사용자는 URL 경로로 자원+행위를 구분하므로 REST의 흔적이 남아있다. "순수 RPC"는 아니다.

### 후보 2: HTTP API / Web API (가장 정직한 이름)
REST도 순수 RPC도 아닌 중간 지대에 잘 맞는다.
**반박:** 너무 뭉뚱그려서 설계 컨벤션 설명으로는 무의미하다.

### 후보 3: 액션/커맨드 기반 API
행위(동사/명령)를 1급 시민으로 다룬다. **CQRS**(Command Query Responsibility Segregation)와 철학이 통한다 — "변경은 POST 명령, 조회는 GET"이 정확히 이 사고방식.
**반박:** 정식 표준 용어가 아니라 관용어. CQRS는 원래 읽기/쓰기 모델·DB까지 분리하는 훨씬 무거운 개념이라, 단순 GET/POST 분리를 CQRS라 부르면 정색당할 수 있다.

### 후보 4: Google의 "커스텀 메서드" — 가장 강력한 선례
구글 공식 API 디자인 가이드가 이 방식을 표준화해놨다:
```
POST /orders/1001:cancel
POST /users/1:sendVerificationEmail
```
논리도 동일: "현실의 많은 동작은 CRUD로 안 떨어진다. 명시적 동사를 POST로 노출하는 게 직관적이다." 준공식 명칭은 **"Resource-oriented design with custom methods"**.
**반박:** 구글은 이를 **예외**로 취급한다. 기본은 표준 메서드, "정 안 되는 것만" 커스텀. 사용자처럼 **기본값을 POST로 두는 것**과는 방향이 반대다.

### 후보 5: "REST-ish" / "RESTless" (반쯤 농담)
"REST인 척하지만 순수 REST는 아닌 것".
**반박:** 밈에 가까워 진지한 아키텍처 명칭으로는 못 쓴다.

### 종합
> **"자원 지향 URL 위에서, 조회는 GET·변경은 커스텀 액션 POST로 표현하는 실용적 RPC-REST 하이브리드"**
> — 구글식: "커스텀 메서드 중심 설계", CQRS식: "커맨드/쿼리를 메서드로 가른 스타일".

**가장 뼈아픈 반박:** 사용자가 최우선으로 두는 "일관성"은 REST 순수주의자도 똑같이 내세우는 명분이다.
- **사용자의 일관성은 지역적(local)**: "이 API 안에서는" 일관적이지만, 여러 API를 넘나들면 각 팀이 URL 동사를 제멋대로 지어(`/cancel`? `/cancellation`? `/abort`?) 표준이 깨질 수 있다.
- **REST의 일관성은 전역적(global)**: GET/POST/PUT/DELETE 4개로 세상 모든 API가 통일된다.

보완하려면 **팀 내부 동사 사전(cancel/publish/archive 표준 목록)을 문서로 못박는 것**이 거의 필수가 된다.

## 9. REST 메서드의 모호함 vs 사설 표준의 실용성

**사용자의 반론:** RESTful이 모든 API를 HTTP 메서드로 담는다지만, `DELETE`의 뜻이 실제로 뭔가? 업서트일 수도, 상태 변경만 할 수도 있다. 너무 모호하다. 반면 상태·변화의 이름은 사실 많지 않아 헷갈릴 일이 적고, URL 표준 시스템을 서비스로 만들어 팀에 공유하면 RESTful보다 낫지 않나?

### 사용자가 맞는 부분

**"DELETE의 뜻이 뭐냐"는 정곡이다.** `DELETE /orders/1001`이 물리 삭제인지, 소프트 딜리트인지, 상태 변경인지 메서드는 말해주지 않는다. 의미의 껍데기만 표현하고 알맹이는 문서에 있다. `PUT`이 업서트로도 순수 교체로도 쓰이는 것도 같은 문제. **"표준이라면서 실제 동작은 팀마다 다르다"** — REST의 명분에 스스로 난 구멍이다.

**"상태/변화의 이름은 많지 않다"는 관찰도 예리하다.** 현실의 상태 전이 동사는 손에 꼽는다(`create`, `cancel`, `publish`, `archive`, `approve`, `activate`, `suspend`...). "동사가 무한히 늘어난다"는 REST 진영의 공격은 과장된 공포인 경우가 많다. 유한하고 사전으로 정리 가능하다.

**따라서 "URL 표준 시스템을 서비스로 만들어 공유하면 RESTful보다 낫다"는 결론은 논리적으로 정당하다.**

### 그래도 남는 반론

1. **모호함을 없앤 게 아니라 이전시킨 것**: REST는 의미를 문서에 숨겼고, 사용자는 URL 동사+표준 서비스로 끌어냈다. 하지만 그 표준 서비스가 새로운 "진실의 원천"이 된다. 서비스가 낡거나 신입이 모르면 `/cancel`과 `/abort`가 다시 갈라진다. REST의 GET/PUT/DELETE는 어디서도 통하는 공용어라 낡을 문서가 필요 없다. **표준을 만드는 것보다 살아있게 유지하는 것이 몇 배 어렵다.**
2. **포기한 것은 "동사 4개"가 아니라 "인프라와의 대화"**: `DELETE`는 모호하지만 멱등 약속을 인프라에 해준다. POST로 통일하면 사람에겐 명확해지지만 기계(로드밸런서, 캐시, 재시도 라이브러리)에겐 깜깜해진다.

## 10. 세 가지 핵심 반박과 그에 대한 정산

사용자가 제기한 세 가지 반박:

### 반박 1: "DELETE도 어차피 취소인지 삭제인지 모르잖아" → **사용자 승**

정확한 급소. REST의 "전역 표준"은 이 경우 **전역적으로 통일된 모호함**일 뿐이다. 정확한 비교는:

- **REST**: 동사는 전역 통일(4개), 대신 의미는 항상 비어서 매번 문서 필요.
- **사용자**: 의미는 URL에 명시(cancel/abort), 대신 동사 통일은 사설 표준에 의존.

즉 **"통일됐지만 빈 REST vs 명확하지만 사설인 사용자"**. 의미 표현력에서는 사용자가 확실히 위다.

**남는 실 한 가닥:** REST의 모호함은 "이 요청을 재시도해도 안전한가"라는 딱 한 질문에 대해서는 안 모호하다. 물리삭제든 소프트딜리트든 `DELETE`인 이상 멱등이 보장된다. REST의 동사는 "의미(what)"는 안 알려주지만 "안전성 성질(how to retry)"은 알려준다. 둘은 서로 다른 것을 표현한다.

### 반박 2: "캐시 필요하면 GET 쓰니까 문제없다" → **절반만 맞음**

캐싱은 GET으로 해결된다 — 맞다. **하지만 캐시는 GET 혜택의 절반이고, 나머지 절반은 "멱등성/재시도 안전성"인데 이건 GET을 남긴다고 안 챙겨진다.**

**시나리오:** `POST /orders/1001/cancel`을 보냈는데 서버는 처리했지만 응답이 유실됨 → 클라이언트가 재시도.
- `DELETE`였다면? 라이브러리가 "멱등하다"는 HTTP 표준을 알아 안심하고 재시도.
- `POST`라면? "위험하다"고 보고 재시도 안 하거나, 직접 멱등성을 보장해야 함.

즉 **"쓰기 요청의 재시도 안전성"은 GET을 남기는 것과 무관한 별개 문제**로 남는다.

### 반박 3: "PUT/PATCH/DELETE는 POST에 이름만 붙인 껍데기 아니냐" → **절반은 맞고 절반은 틀림**

**맞는 절반:** HTTP 메시지 구조(wire format)만 보면 정확하다. PUT/PATCH/DELETE는 POST와 전송 구조가 사실상 같다. 바이트 수준에서 PUT은 "PUT이라 이름 붙은 POST"가 맞다.

**틀린 절반:** 메서드의 가치는 wire format이 아니라 **그 이름에 결속된 "행동 계약(contract)"**에 있다. 계약서도 물리적으로는 잉크 묻은 종이지만, 온 사회가 인정하고 집행하기에 효력을 갖는다. 메서드도 같다:

- **자동 재시도 라이브러리**는 메서드 이름을 보고 재시도 여부를 정한다.
- **로드밸런서/프록시**는 멱등 메서드만 안전하게 failover한다.
- **API 게이트웨이/서비스 메시**(Envoy, Istio)는 메서드 기반으로 재시도·타임아웃 정책을 건다.
- **브라우저**는 POST 재요청에 경고를 띄우지만 GET엔 안 띄운다.

`PUT`이라 쓰는 순간 코드 한 줄 없이도 **전 세계 인프라가 "두 번 보내도 되는구나"라고 알아듣고 행동**한다. 껍데기는 아무도 반응 안 하지만, 이 이름엔 온 생태계가 반응한다.

> "PUT/PATCH/DELETE는 **전송 구조상으로는** POST에 이름 붙인 것뿐이다" → 맞음.
> "PUT/PATCH/DELETE는 **의미·계약상으로도** POST에 이름 붙인 것뿐이다" → 틀림.

### 전체 정산

| 논점 | 결과 |
|---|---|
| 의미 표현력 | **사용자 승** — REST 동사는 "통일된 공백" |
| 캐싱 | **사용자 승** — GET 남기면 해결 |
| 재시도/멱등 안전성 | **남음** — 캐시와 별개, GET 남긴다고 안 챙겨짐 |
| 메서드 = 생태계 행동 계약 | **남음** — wire format은 껍데기지만 이름에 인프라가 반응 |

**논점이 하나로 수렴:** 사용자가 포기하는 유일한 실질은 **"HTTP 메서드 이름에 결속된, 인프라가 자동으로 반응하는 멱등성/안전성 계약"** 하나다.

**진짜 질문:** "내 시스템에서 자동 재시도·failover·멱등 계약을 인프라에 위임할 일이 있는가?"
- **없다면**(멱등성을 애플리케이션 레벨 idempotency key로 직접 관리) → **사용자가 옳다.** 안 쓰는 기능의 표현력을 위해 의미 표현력을 희생할 이유가 없다.
- **있다면**(대규모 분산 시스템, 서비스 메시 위 인프라 레벨 재시도) → 그 부분만큼은 메서드를 남기는 게 공짜 이득.

## 11. 업서트·복수·복합 작동은 어떻게 다루나

**사용자의 질문:** 수정도 되고 생성도 되거나, 복수적인 작동이 있으면?

이것이 REST가 가장 조용히 무너지는 구간이다.

### 경우 1: 업서트 (생성도 수정도)

**REST의 대응은 사실상 없다.** 억지로 `PUT`을 쓰지만, 원래 뜻은 "통째로 교체"지 "없으면 생성"이 아니다. 관행적 해석일 뿐 표준이 아니다. 게다가 생성이면 `201 Created`, 수정이면 `200 OK`를 줘야 하는데 클라이언트는 요청 전엔 뭐가 될지 모른다.

**사용자 방식은 정면으로 표현:**
```
POST /products/save
POST /users/upsert
```
`save`/`upsert`가 "생성일 수도 수정일 수도 있다"는 의도를 명시한다. **논쟁 여지 없이 사용자 승.**

### 경우 2: 복수 작동

**(a) 벌크** — "상품 100개 한 번에 수정"을 REST로? `PATCH /products/1`을 100번? "여러 자원"을 한 요청에 담는 순간 이미 REST가 아니다.
```
POST /products/bulk-update
POST /orders/batch-cancel
```

**(b) 복합 트랜잭션** — "주문 확정" 하나가 실제로는 상태 변경 + 재고 차감 + 결제 + 배송 요청 + 알림 발송. 하나의 동작인데 5개 자원이 바뀐다. 대표 자원 하나를 골라 메서드를 걸 수가 없다. 그래서 **REST 순수주의자조차 결국 `POST /orders/1001/confirm`으로 돌아온다.** 여러 자원을 아우르는 "행위"는 본질적으로 명사가 아니라 동사이기 때문이다. 구글의 커스텀 메서드가 존재하는 이유이기도 하다.

### 그러나 새로 짊어지는 숙제

복합 POST는 여러 자원을 건드리므로 **"부분 실패"와 "중복 실행"** 두 지옥이 동시에 열린다.
- 재고는 차감됐는데 결제 실패 → 유령 상태
- 응답 유실로 재시도 → 결제가 두 번?

이건 사용자 방식의 약점이 아니라 **복합 동작이라는 문제 자체의 본질적 난이도**다. REST로 짰어도 똑같이 겪는다. 그래서 복합 액션엔 다음이 사실상 필수:

1. **멱등성 키(idempotency key)** — 클라이언트가 요청마다 고유 ID를 붙이고, 서버는 "이 키 이미 처리했으면 이전 결과를 돌려줘." Stripe 등 결제 API가 전부 이렇게 한다.
2. **트랜잭션 경계 / 보상(compensation)** — 다 성공하거나 다 롤백(단일 DB면 트랜잭션), 여러 시스템에 걸쳐 있으면 실패 시 되돌리는 보상 로직(사가 패턴).

### 정리

| 상황 | REST | 사용자 방식 |
|---|---|---|
| 업서트 (생성+수정) | `PUT`으로 얼버무림, 모호 | `save`/`upsert`로 명시, **명확** |
| 벌크 (여러 개) | 표현 불가, 억지 | `bulk-*`로 명시, **명확** |
| 복합 트랜잭션 | 결국 액션 URL로 후퇴 | 처음부터 액션 URL, **일관** |

**"생성도 수정도 되거나 복수적인 작동"이야말로 사용자 방식이 REST를 가장 확실하게 앞서는 영역이다.** 여기선 REST가 스스로 무너져 사용자 방식으로 걸어온다. 다만 그 대가로 멱등성 키와 트랜잭션/보상 처리를 직접 설계해야 하며, 이는 이 문제를 다루는 모두의 부담이다.

## 12. 최종 요약

이 논의의 핵심 결론:

1. **REST는 원래 엄격한 철학**(HATEOAS 포함)이었으나, 현실에서는 "HTTP 메서드를 규칙 있게 쓰는 API"(레벨 2) 정도로 느슨하게 통용된다.

2. **"POST 위주 + URL에 목적 명시" 방식은 RESTful이 아니라 RPC-REST 하이브리드**다. 구글의 커스텀 메서드가 가장 강력한 선례이며, 결코 틀린 방식이 아니다.

3. **의미 표현력·업서트·벌크·복합 트랜잭션에서는 이 방식이 REST보다 명확히 우위**다. REST의 `DELETE`/`PUT`은 "통일된 공백"이며, 복합 동작 앞에서는 REST도 결국 액션 URL로 후퇴한다.

4. **이 방식이 포기하는 유일한 실질은 "HTTP 메서드 이름에 결속된 멱등성/안전성 계약"** 하나다. 이는 캐싱과 별개이며 GET을 남긴다고 챙겨지지 않는다.

5. **최종 판단 기준:**
   - 멱등성/재시도를 **애플리케이션 레벨(idempotency key)**에서 직접 관리 → **이 방식이 REST보다 명확하고 실용적이다.**
   - 멱등성/재시도를 **인프라(게이트웨이·서비스 메시)**에 위임하는 대규모 분산 시스템 → 그 부분만큼은 표준 메서드를 남기는 것이 공짜 이득.

6. **일관성의 성격 차이:** 사용자의 일관성은 지역적(조직 내부), REST의 일관성은 전역적. 지역적 일관성을 택했다면 **팀 내부 동사 사전을 서비스로 강제·유지하는 규율**이 성패를 가른다. "승부는 아키텍처가 아니라 조직의 규율에서 난다."

### 미해결 / 다음 단계로 남은 질문

- 복합·복수 동작에서 부분 실패 시 되돌려야 할 것들이 **하나의 DB 안**에 있는가, **여러 시스템(결제사·외부 API)에 걸쳐** 있는가? → "DB 트랜잭션으로 충분하냐, 사가 패턴까지 가야 하냐"가 여기서 갈린다.
- URL 표준 서비스(동사 사전)를 **낡지 않게 설계**하는 방법: 동사 등록·검증·강제 메커니즘, 새 동사 추가 승인 프로세스.
