## 1. 테코톡이란

### 정의

- **10분 테코톡**은 우아한테크코스 크루(교육생)가 동료들 앞에서 기술 주제를 **약 10분간 발표**하는 프로그램. 발표는 녹화되어 "우아한테크" 유튜브 채널의 [10분 테코톡] 재생목록에 공개된다.
- 크루 원문: *"테코톡은 우아한테크코스를 수료하기 위해 최소 1번은 해야하는 10분 정도의 발표를 말합니다. … 이 발표는 녹화되어 유튜브에 업로드됩니다."*
- 공식(우아한형제들 기술블로그): *"각 크루들이 학습한 내용을 테코톡(우아한테크 유튜브)…을 통해 공유하며 함께 성장"*

### 목적

| 관점 | 내용 |
|---|---|
| 발표자 | 지식을 남에게 설명하며 **스스로 깊이 학습** (파인만 기법적 효과) |
| 청중 | 다양한 기술 주제를 짧게 흡수, "아는 지식의 재정리" 효과 |
| 역량 | 현장에서 필요한 **글쓰기·말하기 능력** 훈련 — 우테코 1기 운영 중 커리큘럼에 공식 추가된 배경 |
| 실전성 | 유튜브 공개 = "실전 청중" 앞 발표 경험. *"유튜브에 박제까지 될테니 허투루 준비할 수가 없다"* |

### 운영 방식 (5~6기 기준)

| 항목 | 내용 |
|---|---|
| 발표 시간 | 10분 내외 (실제 13~15분 초과 사례 흔함 — 엄격한 컷보다 '압축 훈련' 장치) |
| 의무 | 수료 요건 — **최소 1회 이상 발표** |
| 주제 선정 | 제약 없음. 운영진이 **예시 주제 시트** 제공 → 예시 중 선택 또는 자유 주제, 신청 후 변경도 가능 |
| 일정 | 매주 목요일 오후 2시, 선릉·잠실 캠퍼스 동시 진행. 타 캠퍼스는 Zoom 실시간 참여 |
| 인원 | 주당 3~4명씩 발표. 2인 짝 발표, 드물게 5인 공동 발표도 존재 |
| 리허설 | 발표 직전 기기·자료 테스트 + 크루들끼리 사전 모의 발표(디스코드 등) 문화 |
| 피드백 | 발표 후 질의응답·토론 + 동료 피드백 |
| 공개 | 녹화 → 우아한테크 유튜브 업로드 |

> 참고: 공식 문서 저장소(woowacourse-docs)에는 테코톡 운영 규칙이 별도 문서화되어 있지 않음. 사실상의 공식 출처는 기술블로그·모집 공고·유튜브 채널.

### 기본 공식

```
[10분 테코톡] {이모지?} {닉네임}의 {주제}
```

- 예: `[10분 테코톡] 🍭 다니의 HTTPS`, `[10분 테코톡] 🌷 코다의 Process vs Thread`
- **이모지**: 1~3기 거의 전부 포함, 4기부터 생략 추세. 발표자별 시그니처 이모지(☂️ 검프 ×6, 🍟 웨지 ×3)로 개인 브랜딩.
- **닉네임 문화**: 실명 대신 크루 닉네임(밧드, 꼬재, 예지니어스, 신세한탄, 손너잘…). 음식·동물·캐릭터 등 자유 작명.

**질문형 제목은 0건** — 전부 명사(구) 형태. 낚시성 수식어 없음. 주제부는 1~6어절로 짧다.

## 4. 발표 내용 구성

발표 정리글 14건(백엔드/네트워크 7 + 프론트/DB/CS 7)에서 추출한 공통 구조.

### 4.1 공통 뼈대: "왜 → 무엇 → 어떻게 → 어디에"

```
① 왜 필요한가 (문제/기원)
② 개념 정의 (무엇인가)
③ 내부 원리 (어떻게 동작하는가)
④ 종류/비교 (무엇과 다른가)
⑤ 실전 적용 (어디에 쓰는가)
```

### 4.2 도입 방식 — 4가지 유형

| 유형 | 방법 | 실제 사례 |
|---|---|---|
| **정의 선행형** | 한 문장 정의를 먼저 못 박음 | 트랜잭션: *"반드시 한번에 이뤄지거나 이뤄지지 않아야 하는 작업의 단위"* / 인덱스: *"검색 성능을 향상시키는 자료 구조"* |
| **문제/기원 서사형** | "기존 방식의 한계 → 그래서 이 기술이 나왔다" | JVM: C/C++의 플랫폼 의존성·크로스 컴파일의 한계부터 → "그래서 JVM이 등장했다" (백엔드 주제에서 가장 설득력 있는 패턴) |
| **선행 개념 사다리형** | 본론 전에 필요한 개념부터 쌓음 | CORS: 에러가 아니라 **Origin의 정의**부터 시작 → SOP → CORS |
| **생활 비유 앵커형** | 일상 비유로 눈높이 맞춤 | Process: *"Program 👉 피자 레시피 = 실행파일 / Process 👉 레시피로 만든 피자"* |
| (변형) 전체 지도 제시형 | 암기법/큰 그림 먼저 | OSI: **"물데네전세표응"** 암기법 → 각론 / 캐시: 메모리 계층 피라미드 먼저 |

**핵심**: 본론 개념을 바로 던지는 발표가 거의 없다. 반드시 **청중이 이미 아는 지점**(일상, 에러 경험, 선행 개념)에서 출발한다.

### 4.3 전개 방식 — 주제 형태별 표준 구조

| 주제 형태 | 구조 | 사례 |
|---|---|---|
| **비교형** (A vs B) | A 단독 설명 → B 단독 설명 → A vs B 표로 수렴 | Process vs Thread, HTTP vs HTTPS, TCP vs UDP |
| **매트릭스형** (두 축) | 축(판별 기준)을 먼저 세우고 → 조합을 채움 | Blocking/Sync: "제어권"과 "결과 관심" 두 축 → 2×2 조합 순회 |
| **파이프라인형** (과정) | 입력→출력을 시간 순서대로 공정 라인처럼 | 브라우저 렌더링: HTML 파싱 → DOM → CSSOM → 렌더트리 → Layout → Paint |
| **연대기형** (버전 있는 기술) | 각 버전의 한계가 다음 버전의 등장 이유가 되는 문제-해결 연쇄 | HTTP/0.9 → 1.0 → 1.1(HOL 블로킹) → 2 → QUIC |
| **계층형** | 하위 계층부터 상향식으로 쌓아 올림. "이전 계층만으로 안 되는 문제 → 다음 계층" | OSI 7계층, 메모리 계층 |
| **심화 사다리형** | 정의 → 성질 → 문제 상황 → 해결책 | 트랜잭션: 정의 → ACID → 이상 현상(Dirty Read 등) → 격리 레벨 |
| **역추적형** (실전 진입) | 최적화 사례로 진입해 원리를 역으로 가르침 | CSS 렌더링 최적화: "top/left 대신 transform을 썼더니 빨라졌다" → Graphics Layer 원리 |

### 4.4 마무리 방식 — 3유형 (이론으로 끝나는 발표가 없다)

1. **요약 1장**: 요약 이미지/5단계 리스트로 전체 재정리 (코다, 체프)
2. **실무 착지**: 스프링 CORS 설정 코드, "읽기:쓰기 = 8:2" 통계, composite 최적화 팁 — "이걸 어디에 쓰는가"로 끝
3. **결론 한 문장 / 다음 주제 연결**: *"Non-Blocking/Async 모델이 가장 유리하다"* / QUIC → HTTP/3 예고 (열린 결말)

## 5. 비유와 예시 사용법

테코톡 표현의 가장 강력한 공통점.

### 원칙 1: "비유 하나로 끝까지 간다"

여러 비유를 흩뿌리지 않고, **하나의 비유를 발표 전체의 앵커**로 쓴다.

- 멍토: **사원-상사 보고 비유 하나**로 Blocking/Non-Blocking/Sync/Async 4조합 전부 설명 — *"상사는 서류를 다 읽는 동안 사원에게 기다리라고 한다"(B) / "읽어볼테니 자리로 돌아가라"(NB) / "결과를 메일로 전달한다"(A)*
- 코다: **회의실 비유** — 멀티프로세스 = *"다른 회의실에서 작업하다 논의할 때만 밖으로"*, 멀티스레드 = *"같은 회의실에서 같은 작업"*
- 체프: 렌더링 레이어 = **포토샵 레이어**

### 원칙 2: "비유(직관) → 실물(검증)" 2단 구성

비유 다음엔 반드시 **개발자가 이미 아는 실제 소프트웨어 사례**로 착지한다.

| 개념 | 비유 | → 실물 사례 |
|---|---|---|
| 멀티프로세스 | 다른 회의실 | **IE vs Chrome 탭** ("크롬은 탭마다 다른 프로세스라 서로 영향이 적다") |
| SOP 부재의 위험 | — | **해커 시나리오**: "http://hacker.hk 링크를 누른다 👉 페이스북 인증 토큰을 약탈당한다" |
| CDN | — | 유튜브의 국제 회선 최적화 |
| will-change | — | 지도 앱: "대기 중엔 해제, 화면 이동 중일 때만 적용" |
| 데이터 지역성 | — | `array[0]→[1]→[2]` for문: "다음에 array[3]에 접근할 확률이 높다" |
| 플랫폼 의존성 | — | "Backend만 Windows용, Linux용, MacOS용이 따로 있는 것" |

### 원칙 3: 정밀함이 필요하면 비유 대신 코드/수치

- DB 트랜잭션: 일상 비유 대신 **실제 SQL**(`UPDATE MEMBER SET AGE = 30 WHERE NAME = '맹'`)로 이상 현상을 재현
- CSS 최적화: **"20프레임 → 75프레임"** 수치 데모로 효과를 정량화
- Preflight: 실제 헤더 포맷(`Access-Control-Request-Method: POST`) 인용

### 시각 자료

전 사례에서 다이어그램이 중심(발표당 3~8개). 4대 유형:
1. **구조도** (메모리 영역, JVM 구조, 계층 피라미드)
2. **흐름도** (SSL 핸드셰이크, 요청-응답 과정)
3. **비교표** (TCP vs UDP, 멀티프로세스 vs 멀티스레드)
4. **상태 전이도** (트랜잭션 상태, 프로세스 상태)

코드는 DB/Java 주제에서만 보조적으로. 슬라이드 다이어그램은 "화살표나 동그라미나 하나하나 손수" 그리는 수제 문화.

## 6. 10분 제약과 분량 전략

### "개념 지도 전체"를 넣고 "깊이"를 버린다

10분에 주제의 **전체 지도**는 다 그리되, 각 지점의 깊이를 희생하는 게 표준 전략.

**공통적으로 버리는 것**: 코드 구현 세부, 성능 측정 방법론, 엔진/벤더별 차이, 동기화·보안 심화.

### 잘된 발표일수록 "생략을 명시적으로 선언"한다

- 인덱스 발표: B+Tree, 다중 컬럼 인덱스, 실행계획을 **"추가로 알아보면 좋을 지식"** 섹션으로 분리 → 청중에게 다음 학습 로드맵을 남김
- OSI 발표: 세션·표현 계층을 생략하며 **근거까지 제시** — *"현대의 인터넷은 OSI 모델이 아니라 TCP/IP 모델을 따른다"*
- 다니의 HTTPS: *"SSL 통신 과정에 중점을 두고 준비했다"* — **핵심 메커니즘 1개에 발표의 무게를 싣는다**고 선언

### 현실

- *"10분이라는 분량 조절도 꽤 어려웠습니다"* — 실제 발표는 13~15분 초과가 흔함
- 슬라이드 40장 넘게 만들었다가 리허설에서 잘라낸 사례
- 10분은 엄격한 컷보다 **'무엇을 버릴지 강제로 결정하게 만드는 압축 훈련 장치'**

## 7. 준비 프로세스

크루 회고 7건에서 수렴된 표준 파이프라인. **타임라인: 최소 2~3주 전 시작.**

### ① 주제 선정 — 3가지 패턴

| 패턴 | 방법 | 사례 |
|---|---|---|
| **미션/프로젝트에서 만난 문제** | 직접 구현·고생한 경험을 주제로. "문제 해결 과정이 드러나는 발표"가 취업 관점에서도 유리하다는 인식 | 웨디: 팀 프로젝트의 에러 핸들링 / 리버: 미션 중 크루들이 반응형 이미지를 수동으로 만들며 고생하던 경험 |
| **범용 기초 개념** | "당장의 공부에 도움 + 전반적 개발 경험에 도움 + 앞으로의 이해에 도움" 3기준 | 루루: "JS만의 개념이 아닌 대부분의 언어에서 쓰이는 개념"이라 Scope/Closure 선택 |
| **청중 수요/공백 노리기** | 사전 설문 또는 아무도 안 한 주제 선점 | 새양: "크루들에게 듣고싶은 도커 내용 정말 많이 물어보기" / 훈동: "소프트스킬 테코톡은 없었어서 선구자가 된 느낌" |

### ② 글로 먼저 쓰기 (가장 체계적인 사례: 웨디의 10단계)

```
목차 작성 → 글 형태로 서술 → 대본 다듬기 → 글 조각내기 → 콘티 작성
→ 슬라이드-대본 매핑 → 슬라이드 제작 → 대본 암기 → 액션(몸짓) 연습
→ 무한 리허설 + 피드백 반영
```

- **대본을 슬라이드보다 먼저, 완결된 글로** 쓴다. 이 글이 그대로 기술 블로그 포스트가 되는 부산물 효과 (*"업로드할 정도로 완성도가 있어"* 별도 게시).

### ③ 슬라이드 전략

- **"핵심 키워드를 여러 장에 우겨넣기"**: 한 장에 다 넣지 않고 여러 장으로 쪼갬 → *"보고 읽는 티도 안 나고 대본을 까먹어도 대응하기 쉽다"*
- 다이어그램은 손수 제작, 발표 전날까지 "PPT 리팩토링" 반복

### ④ 암기 — "대본 통암기"보다 "슬라이드 연상법"이 주류

- 루루: *"대본을 따로 외우지는 않았다. 대본 두 번 본 다음 대본 없이 PPT만 보면서 말하는 연습"* — 약 5회 연습으로 "반자동" 수준
- 리버: *"PPT로 연상법으로 외우다"* — 슬라이드를 기억의 앵커로
- 고강도파(웨디)는 대본 암기 + 몸짓 연습까지

### ⑤ 공개 리허설 (핵심 문화)

- 크루들을 모아 **3~4회 모의 발표** (새양: "월요일 연습 → 새벽까지 피드백 반영 → 수요일까지 총 3~4회")
- 디스코드 원격 모의 발표, 코치(포비)가 참관하는 리허설
- 발표 30분 전 최종 리허설 + 기기/자료 테스트

## 9. 피드백과 공개 문화

### 피드백은 3중 구조

1. **발표 전**: 크루/코치 참관 리허설 → "PPT 리팩토링" 반복
2. **직후**: 질의응답·토론, 크루들의 즉석 칭찬·관련 자료 공유 (*"얘기해본 적 없던 크루가 발표 너무 잘 들었다고"*)
3. **장기**: 유튜브 조회수가 실제 피드백 지표로 작동 (*"생각보다 높은 조회수가 나오지 않아 아쉽다"*)

### 공개 아카이빙의 효과

- **"유튜브 박제"가 준비 강도를 결정하는 최대 변수**: *"유튜브에 박제까지 될테니 허투루 준비할 수가 없다"*
- 발표 후 영상 + 슬라이드 PDF를 본인 블로그에 아카이빙하는 관행
- 시청자들도 발표를 글로 정리해 블로그에 올리며 **References에 테코톡 영상을 명시**하는 규범 → 테코톡이 크루 밖에서도 학습 레퍼런스로 재소비됨 (모아보기 저장소가 만들어질 정도)
- **테코톡 = 글쓰기 부산물 생산**: 대본을 글로 먼저 쓰는 문화 덕에 발표 준비가 그대로 기술 블로그 포스트로 이어짐

## 10. 우리 블로그에 적용할 시사점

우리 블로그(시골쥐×서울쥐 Engineering Blog, `src/blog/STYLE_GUIDE.md`)와 비교해 가져올 것:

### 이미 우리와 일치하는 것 (검증됨)

- 도입 훅에서 "청중이 이미 아는 지점"부터 출발 (우리의 공감 질문/흔한 선택 오프닝)
- 트레이드오프·한계를 스스로 밝히는 정직성
- 수치로 말하기 (테코톡의 "20→75프레임" = 우리의 "인증 트래픽 90% 감소")

### 새로 가져올 만한 것

1. **"비유 하나로 끝까지 간다"** — 우리 글은 비유를 부분적으로 쓰는데, 테코톡처럼 하나의 비유를 글 전체의 앵커로 삼으면 관통력이 커진다. (예: Docker 글의 "붕어빵 틀" 비유를 확장·회수하는 식)
2. **"비유 → 실물 2단 착지"** — 비유 뒤에 반드시 개발자가 아는 실제 소프트웨어(크롬 탭, 유튜브 CDN)로 검증하는 패턴. 일상 사물 비유보다 **"개발자가 이미 아는 소프트웨어" 비유**가 더 효과적.
3. **"생략의 명시적 선언"** — 안 다루는 범위를 숨기지 않고 "추가로 알아보면 좋을 지식"으로 분리해 학습 로드맵을 남기는 것. 글의 신뢰도와 완결성을 동시에 높임.
4. **기원 서사형 도입** — 백엔드 주제는 "기존 방식의 한계 → 그래서 이 기술이 나왔다"가 가장 설득력 있는 도입. (우리 REST 글이 이미 이 구조 — 검증된 셈)
5. **비교형 주제의 표준 구조** — A 단독 → B 단독 → A vs B 표 수렴. 축이 2개면 축부터 세우고 매트릭스 채우기.
6. **주제 형태별 구조 매칭** — 파이프라인 주제는 공정 라인식, 버전 있는 기술은 연대기식, 계층 기술은 상향식. 주제의 형태가 목차를 결정한다.
7. **글 먼저, 슬라이드/포스트는 부산물** — 발표든 블로그든 완결된 글을 먼저 쓰는 프로세스.

### 참고: 제목 전략의 차이

테코톡 제목은 **검색 가능한 개념어 명사형**(질문형 0건), 우리는 **질문형/역발상형**. 이건 매체 차이 — 테코톡은 아카이브/레퍼런스, 우리는 관점을 파는 블로그. 각자 유지가 맞되, 시리즈물·레퍼런스성 글은 테코톡식 명사형("~의 Docker #이론편")도 고려할 만함.
