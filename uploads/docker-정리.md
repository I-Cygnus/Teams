## 1. Docker란 무엇인가

### 한 문장 요약

**Docker는 프로그램을 "실행에 필요한 모든 것과 함께 통째로 포장"해서, 어떤 컴퓨터에서든 똑같이 돌아가게 해주는 도구**다.

### 완전 초보자 관점 — 이사와 컨테이너 비유

프로그램을 만든 사람과 실행하는 사람의 환경이 다르면 "내 컴퓨터에선 되는데 왜 네 컴퓨터에선 안 되지?" 문제가 생긴다. OS가 다르거나, 라이브러리 버전이 다르거나, 설정이 미묘하게 다르기 때문이다.

- 예전 방식: 새 집(새 컴퓨터)에 갈 때마다 가구를 하나하나 다시 사서 조립 → 매번 부품이 안 맞아 고생.
- Docker 방식: **컨테이너(container)** 라는 규격 상자에 앱과 그 앱이 필요로 하는 환경(라이브러리·설정)을 통째로 넣어 옮김 → 어느 집에서 열든 항상 똑같이 작동.

이름이 "Docker(부두 노동자)"이고 로고가 컨테이너 실은 고래인 이유가 여기 있다. 화물 컨테이너의 핵심은 **"안에 뭐가 들었든 규격이 같아서 어느 배·트럭·크레인에나 실린다"** 는 것. Docker는 그 표준화를 소프트웨어에 가져왔다.

### 중급 관점 — VM과의 차이, 이미지와 컨테이너

가장 흔한 질문: "그거 그냥 가상머신 아니야?" → 비슷해 보이지만 핵심이 다르다.

| | 가상 머신(VM) | Docker 컨테이너 |
|---|---|---|
| OS | 앱마다 **완전한 게스트 OS**를 통째로 포함 | 호스트 OS의 **커널을 공유**, 앱+의존성만 포함 |
| 무게 | 무거움 (수 GB, 부팅 수십 초) | 가벼움 (수 초 내 실행) |
| 밀도 | 한 서버에 소수 | 한 서버에 수십~수백 개 |
| 격리 | 아주 강함 | 상대적으로 얕음 |

> "커널을 공유한다"가 무슨 뜻인지는 [2번 섹션](#2-커널이란-무엇인가-그리고-docker와의-관계)에서 자세히 다룬다.

꼭 구분할 두 단어:

- **이미지(image)**: "설계도" 또는 "붕어빵 틀". 앱과 환경을 굳혀놓은, 변하지 않는 파일.
- **컨테이너(container)**: 그 이미지를 실제로 실행한 "붕어빵". 이미지 하나로 컨테이너를 여러 개 찍어낼 수 있다.

작업 흐름:

```text
Dockerfile (무엇을 어떻게 설치·실행할지 기록)
   │  docker build
   ▼
이미지 (변하지 않는 배포 단위)
   │  docker run
   ▼
컨테이너 (실제 실행)
```

만든 이미지는 **Docker Hub** 같은 저장소에 올려두고, 다른 사람이 내려받아 곧바로 실행할 수 있다. 이것이 "내 컴퓨터에선 됐는데" 문제를 없애는 핵심이다.

### 심화 관점 — 내부 동작

컨테이너의 "격리"는 마법이 아니라 리눅스 커널 기능의 조합이다.

- **namespace**: 프로세스가 보는 세계를 쪼갠다(PID·네트워크·마운트·유저 등). 컨테이너 안에서 `ps`를 치면 자기 프로세스만 보이는 이유.
- **cgroups**: 자원(CPU·메모리·I/O)에 상한을 건다. 한 컨테이너가 자원을 독차지하지 못하게 막는다.
- **union filesystem (OverlayFS 등)**: 이미지를 **레이어(layer)** 로 쌓는다. 각 `Dockerfile` 명령이 읽기 전용 레이어 하나가 되고, 실행 시 맨 위에 얇은 쓰기 레이어만 얹는다. 덕분에 공통 레이어를 공유해 디스크·빌드 시간을 아낀다.

이 namespace·cgroups가 전부 **커널의 기능**이라는 점이 중요하다(다음 섹션에서 설명).

## 2. 커널이란 무엇인가 (그리고 Docker와의 관계)

### 커널이란

**커널(kernel)은 운영체제(OS)의 심장, 가장 핵심 부분**이다. 하는 일을 한마디로 하면 **"하드웨어와 앱 사이의 중재자"** 다.

앱은 CPU·메모리·디스크·네트워크 장치를 **직접 만지지 못한다.** 대신 커널에게 부탁한다. "이 파일 읽어줘", "메모리 좀 줘", "이 데이터를 네트워크로 보내줘" 같은 요청을 커널에 보내는데, 이 요청 통로를 **시스템 콜(system call)** 이라고 한다.

```text
        앱 (프로세스)
          │  시스템 콜 ("파일 읽어줘", "메모리 줘")
          ▼
        커널  ← 실제로 하드웨어를 조작
          │
          ▼
   CPU · 메모리 · 디스크 · 네트워크 (하드웨어)
```

커널이 담당하는 대표적인 일:

- **프로세스 스케줄링**: 여러 프로그램 중 누가 언제 CPU를 쓸지 배분.
- **메모리 관리**: 각 프로그램에 메모리를 나눠주고 서로 침범 못 하게 보호.
- **파일시스템**: 디스크의 0과 1을 "파일·폴더"로 다루게 해줌.
- **네트워크 스택**: 패킷을 주고받는 처리.
- **장치 드라이버**: 키보드·그래픽카드 등 하드웨어와 대화.
- **권한·보안**: 누가 무엇에 접근할 수 있는지 통제.

**OS = 커널 + 그 위의 사용자 공간 도구**(셸, 라이브러리, 유틸리티)라고 보면 된다. 예를 들어 우분투와 페도라는 겉모습(사용자 공간)은 다르지만 **둘 다 리눅스 커널**을 쓴다.

> **비유:** 커널은 건물의 관리실/설비실이다. 입주자(앱)는 전기·수도·엘리베이터를 직접 조작하지 않고 관리실에 요청한다. 관리실이 실제 설비를 안전하게 돌린다.

### Docker와 무슨 상관 — 왜 "커널 공유"가 핵심 트릭인가

컨테이너 안의 앱도 결국 시스템 콜로 커널에 일을 시킨다. 그런데 **컨테이너는 자기만의 커널이 없다.** 호스트의 커널에 직접 요청한다. 이것이 "커널을 공유한다"의 진짜 의미다.

- 앞 섹션의 **namespace·cgroups가 바로 이 커널의 기능**이다. 커널이 "이 프로세스에겐 세상을 이만큼만 좁게 보여줘"(namespace) + "자원은 이만큼만 써"(cgroups) 하고 처리해 주는 것. 즉 **컨테이너의 격리는 커널이 제공하는 서비스**다.
- **VM은 반대**다. 게스트 OS가 자기 커널을 통째로 품는다. 그래서 무겁지만 커널 수준까지 완전히 분리된다.

```text
[Docker 컨테이너]              [가상 머신]
  앱 A   앱 B                    앱 A        앱 B
   └───┬───┘                   게스트 커널  게스트 커널
   호스트 커널 (하나를 공유)         └────┬────┘
      하드웨어                     하이퍼바이저
                                    호스트 커널
                                    하드웨어
```

### 커널을 공유하기 때문에 생기는 영향

1. **가벼움의 근원**: 커널을 새로 안 올리니 부팅 과정이 없다. 그래서 컨테이너가 수 초 만에 뜬다.
2. **커널 종속 (플랫폼 제약)**: 컨테이너는 호스트 커널을 그대로 쓰므로 "리눅스 컨테이너 = 리눅스 커널 필요". 맥·윈도우에서 리눅스 VM이 필요한 이유가 바로 이것 — 그 VM이 리눅스 커널을 제공한다([4번 섹션](#4-호스트-os리눅스맥윈도우가-달라도-잘-되나) 참고).
3. **커널 버전·기능 의존**: 컨테이너가 특정 커널 기능(예: 최신 시스템 콜)을 쓰는데 호스트 커널이 너무 오래됐으면 문제가 될 수 있다. 대개는 호환되지만, 극단적인 경우 걸린다.
4. **격리의 한계 = 보안 영향**: 모든 컨테이너가 **같은 커널 하나를 공유**한다. 그래서 커널에 취약점이 있으면 컨테이너 탈출(container escape)로 호스트나 옆 컨테이너까지 영향이 갈 수 있다. VM보다 "공유 지점"이 크다는 뜻. 신뢰할 수 없는 워크로드에는 gVisor·Kata Containers 같은 추가 격리를 얹는 이유다.
5. **CPU 아키텍처 종속**: 커널과 실행 바이너리는 CPU 명령어 집합에 묶인다. x86(amd64)용 이미지가 ARM(애플 실리콘)에서 그대로 안 도는 문제가 여기서 나온다.

> **한 줄 정리:** VM은 "커널까지 통째로 복제"해서 무겁지만 강하게 분리하고, Docker는 "커널 하나를 여러 컨테이너가 나눠 쓰되 커널의 격리 기능으로 칸막이"를 쳐서 가볍다. 그래서 Docker의 장점(가벼움)과 제약(커널·아키텍처 종속, 얕은 격리)은 모두 "커널 공유"라는 한 뿌리에서 나온다.

## 3. 가상 머신(VM)이란

VM은 **소프트웨어로 만든 "가짜 컴퓨터" 한 대**다. 진짜 컴퓨터 위에서, 별도의 물리 컴퓨터가 여러 대 있는 것처럼 흉내 낸다.

이를 가능하게 하는 것이 **하이퍼바이저(hypervisor)** 다. 하이퍼바이저는 진짜 하드웨어의 CPU·메모리·디스크를 쪼개 각 VM에게 "이건 네 하드웨어야" 하고 나눠준다. 그러면 각 VM은 자기가 진짜 컴퓨터 위에 있다고 착각하고, 그 안에 **자기만의 완전한 OS(커널까지)** 를 깔아 돌아간다.

하이퍼바이저 종류:

- 하드웨어 위에 바로 얹는 것: ESXi, KVM, Hyper-V (서버용)
- 이미 깔린 OS 위에서 앱처럼 돌리는 것: VirtualBox, VMware Workstation

특징: 각 VM이 진짜 OS를 통째로 품으니 **격리는 아주 강하지만 무겁다**(부팅 수십 초, 용량 수 GB, 다수 실행 어려움).

## 4. 호스트 OS(리눅스·맥·윈도우)가 달라도 잘 되나?

**"자동으로 아무 데서나 다 된다"는 아니다.** 컨테이너는 호스트 커널을 공유하므로 근본적으로 **커널 종류에 묶여 있다.**

- **리눅스 호스트**: 리눅스 컨테이너가 커널 위에서 바로(네이티브) 실행.
- **맥 / 윈도우 호스트**: 리눅스 커널이 없으므로, Docker Desktop이 **뒤에서 가벼운 리눅스 VM을 하나 돌리고** 그 안에서 컨테이너를 실행한다(윈도우는 주로 WSL2, 맥은 가상화 프레임워크). 사용자 눈엔 그냥 되는 것처럼 보이지만, 실제로는 리눅스 위에서 도는 것.

```text
[리눅스 호스트]                 [맥 / 윈도우 호스트]
  컨테이너                        ┌ 숨겨진 리눅스 VM ┐
  리눅스 커널                     │  컨테이너         │
  하드웨어                        │  리눅스 커널(VM)  │
                                 └ 맥/윈도우+가상화 ┘
  → 커널 위에서 바로 실행            하드웨어
```

즉 컨테이너가 진짜 묶여 있는 건 "호스트 OS 종류"가 아니라 **"커널 종류 + CPU 아키텍처"** 다. 그래서 실제로 걸리는 두 가지:

1. **CPU 아키텍처**: x86(amd64)용 이미지는 애플 실리콘(ARM) 맥에서 그대로 못 돌 수 있다. 멀티 아키텍처 이미지나 에뮬레이션(QEMU/Rosetta)으로 해결. "왜 내 M1 맥에서 이 이미지가 안 뜨지?"의 흔한 원인.
2. **윈도우 컨테이너는 별개**: 윈도우 커널이 필요하며 윈도우 호스트에서만 돌고, 리눅스 컨테이너와 섞이지 않는다. 보통 "Docker"라고 하면 대부분 리눅스 컨테이너를 가리킨다.

## 5. JAR만 바꿀 때 다시 빌드해야 하나?

**원칙적으로는 "이미지를 다시 만들어 새 컨테이너로 교체"가 정석이다.** 이미지는 한번 구우면 안 바뀌는(immutable) 파일이고, 이미 떠 있는 컨테이너는 옛 이미지의 복사본이라 JAR만 바꿨다고 저절로 반영되지 않는다.

전형적인 `Dockerfile`:

```dockerfile
FROM eclipse-temurin:21-jre
COPY app.jar /app.jar
ENTRYPOINT ["java", "-jar", "/app.jar"]
```

정석 배포 과정:

1. 새 JAR 빌드: `./gradlew build` (또는 `mvn package`)
2. 이미지 재빌드: `docker build -t myapp:1.1 .`
3. 옛 컨테이너 내리고 새로 띄우기: `docker stop`/`docker rm` 후 `docker run`, 또는 Compose면 `docker compose up -d --build` 한 방

### 매번 전부 다시 빌드하면 느리지 않나? → 아니다 (레이어 캐시)

Docker는 이미지를 레이어로 쌓고, **바뀌지 않은 레이어는 캐시**해서 재사용한다. 바뀐 레이어와 **그 위쪽만** 다시 만든다.

```text
┌───────────────────────────┐
│ COPY app.jar  ← 바뀜: 다시 빌드│  (이 층만 새로 만듦)
├───────────────────────────┤
│ 의존성/라이브러리 ← 캐시 재사용 │
├───────────────────────────┤
│ 베이스 이미지(JRE) ← 캐시 재사용│
└───────────────────────────┘
```

**핵심 원칙: 자주 바뀌는 것(JAR)은 위에, 안 바뀌는 것(의존성)은 아래에 둔다.**

스프링 팁: **레이어드 JAR(layered jar)** 을 쓰면 뚱뚱한 JAR을 "잘 안 바뀌는 의존성"과 "자주 바뀌는 내 코드"로 나눌 수 있다. 이를 `Dockerfile`에서 각각 다른 `COPY` 레이어로 넣으면, 코드만 고쳤을 때 무거운 의존성 레이어는 캐시로 재사용돼 빌드·배포가 훨씬 빨라진다.

### 개발 중 빠른 반복을 위한 지름길 (이미지 재빌드 없이)

- **바인드 마운트**: 이미지에 JAR을 굽지 말고 호스트의 JAR을 컨테이너에 연결.
  `docker run -v ./build/libs/app.jar:/app.jar ...` → JAR만 새로 빌드해 덮어쓰고 `docker restart`.
- **`docker cp`**: 실행 중 컨테이너에 파일만 밀어넣기.
  `docker cp app.jar 컨테이너:/app.jar` 후 재시작.
- **스프링 부트 DevTools**: 클래스가 바뀔 때 자동 재시작.

정리: **운영 배포는 "이미지 재빌드로 통째 교체"가 정석**(재현 가능·안전), 레이어 캐시 덕에 실제론 빠르며, **개발 중 빠른 반복은 바인드 마운트 같은 지름길**을 쓴다.

---

## 6. 바인드 마운트 vs 볼륨

느낌은 비슷하지만 **엄밀히는 다르다.** (앞서 `-v ./app.jar:/app.jar` 예시는 정확히는 바인드 마운트다.)

| | 바인드 마운트 | 볼륨(volume) |
|---|---|---|
| 위치 지정 | **내가 직접** 호스트 경로 지정 | **Docker가 알아서** 관리(`/var/lib/docker/volumes/...`) |
| 용도 | JAR 바꿔치기, 소스 연결 등 | DB 데이터처럼 안전하게 살아남아야 하는 데이터 |
| 명령어 | `-v ./app.jar:/app.jar` (호스트 경로 O) | `-v mydata:/var/lib/...` (이름만) |

> 둘 다 `-v` 플래그를 써서 헷갈린다. **호스트 경로를 주면 바인드 마운트, 이름만 주면 볼륨.**

바인드 마운트로 JAR을 연결해두고 JAR만 새로 빌드해 덮어쓰면 새 파일이 컨테이너 안에서 바로 보인다. 단, **컨테이너(또는 java 프로세스)를 재시작**해야 반영된다 — 실행 중인 JVM은 옛 JAR을 메모리에 올려둔 상태라 저절로 다시 읽지 않는다. `docker restart 컨테이너이름`이면 된다.

> **실무 팁:** 단일 파일 하나만 마운트하기보다 **JAR이 든 폴더를 통째로 마운트**하는 게 안정적이다. 빌드 도구가 JAR을 "덮어쓰기"가 아니라 "지우고 새로 생성"하면 파일 실체(inode)가 바뀌어, 단일 파일 마운트가 옛 파일을 계속 가리키는 문제가 생길 수 있다.

## 7. 알아두면 좋은 실무 지식

### 이미지를 잘 만드는 법

**멀티 스테이지 빌드(multi-stage build)** — 자바에서 임팩트가 크다. 빌드엔 JDK+Gradle이 필요하지만 실행엔 JRE+JAR만 있으면 된다. 무거운 빌드 도구는 최종 이미지에 남기지 않는다.

```text
[빌드 단계 — 버려짐]              [실행 단계 — 최종 이미지]
  JDK + Gradle                      JRE (가벼움)
  소스 코드           ── JAR만 복사 ▶  app.jar
  app.jar 생성
```

```dockerfile
FROM eclipse-temurin:21-jdk AS build
WORKDIR /app
COPY . .
RUN ./gradlew build

FROM eclipse-temurin:21-jre
COPY --from=build /app/build/libs/app.jar /app.jar
ENTRYPOINT ["java", "-jar", "/app.jar"]
```

**베이스 이미지 선택**: `jdk`(개발용, 큼) vs `jre`(실행용, 작음). `-alpine`·distroless 같은 초경량도 있으나, alpine은 다른 C 라이브러리(musl)를 써서 드물게 네이티브 라이브러리가 말썽일 수 있다. 자바는 무난하게 `-jre` 계열로 시작 권장.

**태그의 함정**: `latest`는 "최신"이라는 약속이 아니라 기본 태그 이름일 뿐이고 언제든 다른 내용을 가리킬 수 있다. 운영에선 `myapp:1.4.2`처럼 버전을 박아 쓰는 게 안전하다.

### 컨테이너를 잘 굴리는 법

**설정은 이미지에 굽지 말고 실행 시 환경 변수로 주입**한다. `docker run -e SPRING_PROFILES_ACTIVE=prod ...` 처럼. 스프링은 `SPRING_DATASOURCE_URL` 등 환경 변수를 알아서 읽는다. **비밀번호·API 키는 절대 이미지에 넣지 말 것** — 이미지 레이어 기록(history)에 남아 나중에 지워도 흔적이 남는다.

**컨테이너끼리는 이름으로 통신**한다. 같은 Docker 네트워크(Compose면 자동 구성) 안에서는 IP가 아니라 컨테이너/서비스 이름(예: `db`)을 호스트명처럼 쓴다. 컨테이너에서 호스트 컴퓨터로 접속하려면 `host.docker.internal`.

**매일 쓰는 디버깅 명령어:**

```bash
docker logs -f 컨테이너        # 로그 실시간 보기
docker exec -it 컨테이너 sh    # 컨테이너 안으로 들어가 셸 열기
docker ps                     # 돌아가는 컨테이너 목록
docker inspect 컨테이너        # 상세 정보
docker stats                  # 자원 사용량
```

**자동 재시작 & 헬스체크**: `--restart unless-stopped`를 주면 재부팅·크래시 후에도 다시 뜬다. `HEALTHCHECK`로 정상 여부를 주기적으로 확인하면 더 튼튼하다.

**JVM과 컨테이너 메모리 함정 (자바 필독)**: 컨테이너에 메모리 상한(`--memory=512m`)을 걸면, 옛날 JVM은 그 상한을 못 보고 호스트 전체 메모리 기준으로 힙을 잡다가 강제 종료(OOM Kill)되곤 했다. 이 상한 자체가 커널의 cgroups 기능인데, 요즘 JVM(자바 10+, 8도 최신 패치)은 이 cgroups 값을 읽는 "컨테이너 인식"이 기본이다. 그래도 `-XX:MaxRAMPercentage`로 힙 비율을 명시하는 게 안전하다.

### 뒷정리와 안전

**디스크가 조용히 차오른다**: 빌드할 때마다 안 쓰는 옛 레이어(dangling image)·멈춘 컨테이너·안 쓰는 볼륨이 쌓인다. 가끔 `docker system prune`으로 정리(볼륨까지 지우려면 옵션 필요 — 데이터 주의).

**안전 습관**: 프로세스를 기본값 root로 돌리지 말고 `Dockerfile`에 `USER`로 일반 사용자 지정, 비밀정보는 이미지에 넣지 않기, Trivy·docker scout로 이미지 취약점 스캔. (커널을 공유하는 구조라 컨테이너 안 root가 호스트에 미칠 위험이 VM보다 크다는 점을 기억.)

## 8. 실전 예시: 프론트 + 백엔드 + AI 서비스 배포

앞의 조각들을 실제 프로젝트 하나로 합쳐 본다. 흔한 구성인 **React 프론트엔드 + Spring Boot 백엔드 + Python AI 서비스 + PostgreSQL DB**, 그리고 이들을 하나로 묶는 **nginx 리버스 프록시**를 예로 든다.

### 8.1 전체 그림

```text
                        사용자 브라우저
                             │  :80
                             ▼
                     ┌────────────────┐
                     │  proxy (nginx)  │  ← 외부에 공개되는 유일한 문
                     └───┬────────┬────┘
              "/"        │        │   "/api/*"
                         ▼        ▼
                 ┌────────────┐  ┌──────────────┐
                 │  frontend   │  │   backend     │
                 │ 정적/nginx   │  │ Spring :8080  │
                 └────────────┘  └───┬───────┬───┘
                              "/predict"      │ JDBC
                                    ▼         ▼
                            ┌────────────┐  ┌──────────────┐
                            │ ai FastAPI  │  │ db PostgreSQL │
                            │   :8000     │  │    :5432      │
                            └────────────┘  └──────┬───────┘
                                                   │ volume
                                            [ db-data 영속 저장 ]
```

요청 흐름: 브라우저가 프록시(:80)에 접속 → `/`는 프론트엔드 정적 파일, `/api/*`는 백엔드로 전달 → 백엔드는 필요 시 AI 서비스(`/predict`)를 호출하고 DB에 질의 → 결과를 되돌려준다. **오직 프록시만 외부 포트를 열고**, 나머지 서비스는 내부 네트워크에서만 서로 부른다(공격 표면 최소화).

### 8.2 폴더 구조

```text
myproject/
├─ docker-compose.yml      # 서비스 5개를 묶는 오케스트레이션 파일
├─ .env                    # 비밀값(DB 비밀번호 등) — git에는 올리지 않음
├─ frontend/               # React (Vite)
│  ├─ Dockerfile
│  ├─ nginx.conf
│  └─ .dockerignore
├─ backend/                # Spring Boot
│  ├─ Dockerfile
│  └─ .dockerignore
├─ ai/                     # Python FastAPI
│  ├─ Dockerfile
│  ├─ main.py
│  ├─ requirements.txt
│  └─ .dockerignore
└─ proxy/
   └─ nginx.conf
```

각 서비스는 자기 폴더에 자기 `Dockerfile`을 갖는다. 서비스마다 필요한 환경(Node, JDK, Python)이 다르므로 이미지도 따로 만드는 게 자연스럽다.

### 8.3 각 서비스의 Dockerfile

**프론트엔드** — Node로 빌드해 정적 파일을 만들고, 그 결과만 가벼운 nginx로 서빙(멀티 스테이지).

```dockerfile
# 1) 빌드 단계
FROM node:20 AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build          # 결과물: /app/dist

# 2) 서빙 단계
FROM nginx:1.27-alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
```

> 주의: Vite·React 같은 프론트엔드는 API 주소 같은 값이 **빌드 시점에 코드로 굳는다.** 즉 백엔드처럼 실행 시 `-e`로 바꾸는 게 아니라, 빌드할 때 `ARG`/`--build-arg`로 넣어야 한다. 백엔드 환경 변수와 성격이 다르니 헷갈리지 말 것.

**백엔드(Spring Boot)** — JDK로 JAR을 만들고 JRE로 실행(멀티 스테이지).

```dockerfile
FROM eclipse-temurin:21-jdk AS build
WORKDIR /app
COPY . .
RUN ./gradlew clean bootJar -x test

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /app/build/libs/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

**AI 서비스(Python FastAPI)**

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

> AI 서비스는 **모델 파일이 수백 MB~수 GB**가 되기도 한다. 선택지: (1) 이미지 빌드 시 모델을 내려받아 포함(이미지가 커지지만 배포가 단순), (2) 모델을 볼륨으로 마운트(이미지는 가볍지만 실행 환경에 모델을 따로 둬야 함). GPU를 쓰면 NVIDIA Container Toolkit이 추가로 필요하다.

### 8.4 서비스를 묶는 docker-compose.yml

```yaml
services:
  proxy:
    image: nginx:1.27-alpine
    ports:
      - "80:80"                       # 외부에 여는 유일한 포트
    volumes:
      - ./proxy/nginx.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on: [frontend, backend]

  frontend:
    build: ./frontend                 # 내부 포트만 사용, 호스트에 노출 안 함

  backend:
    build: ./backend
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/appdb
      SPRING_DATASOURCE_USERNAME: app
      SPRING_DATASOURCE_PASSWORD: ${DB_PASSWORD}
      AI_SERVICE_URL: http://ai:8000  # 서비스 이름이 곧 주소
    depends_on:
      db:
        condition: service_healthy    # DB가 준비된 뒤에 뜸

  ai:
    build: ./ai

  db:
    image: postgres:16
    environment:
      POSTGRES_DB: appdb
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - db-data:/var/lib/postgresql/data   # 데이터 영속화
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 5s
      retries: 5

volumes:
  db-data:
```

그리고 비밀값은 `.env` 파일에 둔다(이미지에 굽지 않는다):

```text
# .env
DB_PASSWORD=super-secret-value
```

이 파일이 만들어내는 핵심 동작들:

- **서비스 이름 = 주소**: 백엔드가 DB를 `db:5432`, AI를 `http://ai:8000`으로 부른다. IP도 `localhost`도 아니다 — Compose가 만든 내부 네트워크에서 서비스 이름이 호스트명 역할을 한다.
- **외부 노출 최소화**: `ports`로 호스트에 포트를 여는 건 프록시뿐. frontend·backend·ai·db는 바깥에서 직접 접근 불가. 이게 곧 보안이다.
- **비밀값 분리**: `${DB_PASSWORD}`는 `.env`에서 주입 → 이미지 히스토리에 남지 않는다.
- **기동 순서 제어**: `depends_on` + `healthcheck`로 DB가 정상이 된 뒤에 백엔드가 뜬다.
- **데이터 영속**: `db-data` 볼륨 덕에 컨테이너를 지워도 DB 내용은 살아남는다.

프록시 라우팅(`proxy/nginx.conf`)은 이런 식이다:

```nginx
server {
  listen 80;
  location /api/ { proxy_pass http://backend:8080/; }
  location /     { proxy_pass http://frontend:80/; }
}
```

### 8.5 로컬에서 한 번에 띄우기

```bash
docker compose up --build
```

이 한 줄로 다섯 서비스의 이미지가 빌드되고, 내부 네트워크와 볼륨이 만들어지고, 올바른 순서로 전부 뜬다. 브라우저에서 `http://localhost` 하나로 앱 전체가 동작한다. 내리려면 `docker compose down`(데이터까지 지우려면 `-v`).

### 8.6 개발 → 운영 배포 흐름

로컬에서 검증했으면, 운영 서버로 가져가는 흐름은 이렇다.

1. **이미지 빌드 & 태그**: 서비스별로 버전 태그를 붙여 이미지를 굽는다.
   `docker build -t myrepo/backend:1.2.0 ./backend` (프론트·AI도 동일)
2. **레지스트리에 푸시**: Docker Hub, GitHub Container Registry(GHCR), AWS ECR 등에 올린다.
   `docker push myrepo/backend:1.2.0`
3. **운영 서버에서 내려받아 실행**: 운영용 compose는 `build:` 대신 이미 만든 **`image:`** 를 가리키게 한다.
   ```yaml
   backend:
     image: myrepo/backend:1.2.0     # 서버에선 빌드하지 않고 받아서 실행
   ```
   서버에서 `docker compose pull && docker compose up -d`.
4. **업데이트(롤링 교체)**: 새 버전 이미지를 푸시하고, 서버에서 다시 `pull` 후 `up -d` 하면 바뀐 서비스만 새 컨테이너로 교체된다.
5. **CI/CD로 자동화**: `git push` → CI(GitHub Actions 등)가 빌드·테스트·이미지 푸시 → 서버가 새 이미지를 받아 교체. 사람 손을 뺀다.

```text
개발자 push
   │
   ▼
CI: 빌드 → 테스트 → 이미지 push (레지스트리)
   │
   ▼
운영 서버: pull → compose up -d (바뀐 서비스만 교체)
```

### 8.7 여기서 한 단계 더

지금은 **한 대의 서버**에서 Compose로 돌리는 그림이다. 트래픽이 커져서 서버가 여러 대가 되고, "AI 서비스만 3개로 늘려라", "무중단으로 업데이트하라", "죽으면 자동 복구하라" 같은 요구가 생기면 Compose로는 한계가 온다. 그때가 **Kubernetes**로 넘어갈 시점이다. 중요한 건, 지금 만든 **이미지와 서비스 분리 구조는 그대로 재사용**된다는 점 — Kubernetes는 그 이미지들을 더 똑똑하게 배치·관리해줄 뿐이다.

---

## 9. 다음 단계

1. **Docker Compose** — 스프링 앱과 DB 컨테이너를 `docker-compose.yml` 한 파일에 묶어 `docker compose up` 한 번에 실행.
2. **Kubernetes** — 컨테이너가 많아지고 서버가 여러 대가 되면 배포·복구·롤링 업데이트를 자동 관리.

지금 스프링을 다루고 있다면, 실습으로는 **멀티 스테이지 `Dockerfile` + Compose로 앱과 DB 묶기**가 가장 남는 게 많다.

## 핵심 한 줄 요약

- **커널**: 하드웨어와 앱 사이의 중재자. Docker는 이 커널 하나를 여러 컨테이너가 공유한다 → 가벼움의 근원이자 제약(커널·아키텍처 종속, 얕은 격리)의 뿌리.
- **초보자**: 환경째로 포장해서 어디서든 똑같이 돌리는 상자.
- **중급자**: OS(커널)를 공유해 VM보다 가벼운 격리 실행 단위 + 이미지로 배포.
- **심화**: 리눅스 namespace·cgroups·union FS를 조합한, OCI 표준 기반 컨테이너 생태계의 대표 구현체.
