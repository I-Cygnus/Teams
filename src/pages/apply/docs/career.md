## Trouble Shooting 경험

**(스택 트레이스 오독) OOM의 범인은 맨 위에 없었다**
초기 분석서는 스택 최상단의 Producer를 범인으로 지목했습니다. 그러나 메모리를 거의 쓰지 않는 유휴 스레드까지 같은 시각에 죽어 있었습니다. 이는 힙 전체가 고갈됐다는 뜻이고, 스택 맨 위는 "마지막으로 할당을 요청했다 거절당한 자"일 뿐입니다. 질문을 "누가 호출됐나"에서 "누가 점유했나"로 바꾸자 30분 만에 실제 원인 코드에 도달했습니다. 이후 장애 분석에서 발생 지점과 원인 지점을 구분하는 것을 첫 번째 원칙으로 삼고 있습니다.

**(자기 코드 의심) 배포 직후 "정확히 1건"의 의미**
커넥션 풀 수정 배포 후 결과가 정확히 1건만 저장되는 증상이 보고됐습니다. "정확히 1건"이라는 규칙성에서 무작위 장애가 아니라 결정적 코드 문제임을 직감했고, 제가 작성한 폴백 코드의 `Math.max(0,1)=1` — 설정값 0이 기본값 100이 아니라 1로 폴백되는 결함임을 몇 분 만에 확인했습니다. 방금 고친 코드가 다음 버그의 1순위 용의자라는 원칙이 여기서 생겼습니다.

**(운영 사고) WHERE 없는 UPDATE**
운영 DB에서 WHERE 절이 누락된 UPDATE를 실행하는 사고를 냈습니다. 즉시 원복 절차를 수립해 복구했고, 이후 모든 운영 SQL을 멱등하게, 롤백문과 함께 작성하는 것을 개인 표준으로 만들었습니다. 작업 전 절차를 적어두고 적용 직전에 다시 읽는 습관도 이 사고에서 나왔습니다.

**(컨테이너의 함정) ENTRYPOINT를 덮어쓴 command**
JVM에 힙 옵션을 분명히 설정했는데도 컨테이너가 900MiB 이상을 점유했습니다. 추적 결과 docker-compose의 `command`가 Dockerfile의 `ENTRYPOINT`를 통째로 덮어써 옵션이 사라진 것이 원인이었습니다. `exec java $JAVA_OPTS` 형태로 수정해 java가 PID 1을 차지하고 종료 시그널을 정상 수신하도록 함께 정리했습니다.

**(아키텍처 불일치) ARM에서 빌드한 이미지의 exec format error**
로컬(Apple Silicon)에서 빌드한 이미지를 x86 서버에 올려 컨테이너가 즉사했습니다. 로그는 `exec format error` 한 줄. 이후 CI에서 `platforms: linux/amd64`를 명시해 재발 경로를 차단했습니다.

**(표기의 정합성) 더 나은 설계를 스스로 되돌린 일**
개선활동 진행단계를 더 정확하게 판정하는 서버 로직을 설계·구현했지만, 기존 화면과 표기가 달라지면 사용자가 혼란을 겪는다고 판단해 기존 표기에 맞추는 쪽으로 되돌렸습니다. 대신 설계 전체를 배경·근거·코드·검증 방법과 함께 백업해, 문서만 보고 완전 복원이 가능하게 남겼습니다. 기술적 우위보다 제품의 일관성이 우선일 때가 있다는 것을 이 일로 배웠습니다.
