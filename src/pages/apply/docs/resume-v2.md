## Work Experience

### 엔코아 (en-core) | 2026.02 ~ 재직 중
DataWare 7.0 데이터 거버넌스 플랫폼 — 데이터 품질(DQ5)·민감데이터 검출(SDX) 영역

**① JVM OOM 근본 원인 규명 — 오진 교정** `Java 21 · Spring Boot · Rust · PostgreSQL`
- 상황: 920만 행 컬럼 분석 작업이 OOM으로 사망. 재현 환경 없음, 증거는 모니터를 찍은 사진 2장과 "스택 최상단 Producer의 문자열 연결이 원인"이라는 초기 분석서뿐
- 판단: RMI idle 스레드·HttpClient 셀렉터까지 동시에 OOM — 특정 컴포넌트가 아니라 힙 전체 고갈. Producer는 마지막으로 할당을 요청했다 거절당한 피해자
- 행동: 질문을 "누가 마지막에 호출됐나"에서 "누가 힙을 점유했나"로 전환 → Consumer에서 `DATA_SAVE_CNT == 0`이 무제한 적재로 해석되는 코드 발견 → git 이력에서 과거 "결과 미적재 버그"를 고치며 한도를 풀어버린 회귀 커밋 특정
- 결과: 모든 설정 경우에 결과 버퍼 ≤ 100건 보장, `-Xmx` + OOM 시 힙덤프 자동 확보 체계 구축. "0=무제한" 매직 값 자체를 제거
- 추가: MySQL JDBC가 `fetchSize`를 무시하고 전체 ResultSet을 적재하는 함정(`useCursorFetch` 부재)을 발견해 동일 OOM의 제2 경로 사전 차단 — 대용량 잠재 리스크 9건 사전 발굴

**② 커넥션 풀 사이징 결함 — 수요 모델 재설계**
- 상황: OOM 수정 후 2차 증상으로 커넥션 타임아웃. "풀을 늘리자"는 대응은 근본 해결이 아니라고 판단
- 진단: 공급은 N(설정값), 수요는 2N+2(작업당 2 + 관리 2) — 구조적 불일치
- 설계: 수요 모델에서 풀 크기를 역산하는 산정식 + 거버넌스 3계층(작업당 병렬수 상한 → 동시 작업 상한 → DB 계정 CONNECTION LIMIT) → 최악 시나리오에서도 총량 상수 72
- 자체 검증: 구현 후 적대적 재검토로 심각 결함 1건 추가 발견 — Manager에서 clamp한 병렬수를 자식 프로세스가 DB 재조회로 우회하는 문제. 값이 흐르는 전 구간(Manager→CLI 인자→매퍼→핸들러) 추적으로 확정
- 배포 직후 자신이 작성한 폴백 코드의 결함(설정값 0이 100이 아닌 1로 폴백)을 "정확히 1건" 증상에서 역추적해 자체 수정

**③ 운영 DB 300GB 이상 점유 — 스캔 없는 확정 진단** `PostgreSQL 16`
- 상황: 프로파일링 상세 테이블 300GB, 요약 테이블 22MB. "데이터 유실" 의심이 먼저 제기됨
- 진단: 운영 DB라 전체 스캔 불가 판단 → `pg_stat_user_tables` → heap/TOAST/index 분해 → `pg_class.relpages` 3,662만 페이지 vs 유효 행 31만(페이지당 0.009행) 3단계로 "유실이 아니라 99.9%가 빈 페이지(bloat)" 확정 — 디스크풀 크래시의 잔해임을 시점 증거와 함께 규명
- 결과: DELETE + VACUUM FULL로 300GB 회수. 재발 방지로 `pgstattuple_approx` 기반 [테이블 운영 지표] 화면·API를 신규 개발 (정확도 vs 운영 부하 트레이드오프를 검토해 근사 함수 채택, 근거 문서화)

**④ 기능 개발 · 분석 · 문서화**
- [개선활동 상태] 화면 신설 — 3계층 트리·진행상태 5분류·업무영역 권한 + 담당자 4역할 조회범위를 3개 저장소에 걸쳐 단독 개발
- 운영 이슈 10건+ 코드·SQL 레벨 규명 (선분이력 갱신으로 인한 재실행 상태 오작동, 엔진 INSERT 시 status NULL로 인한 진행중 오판정 등)
- 백엔드/프론트/엔진 3개 저장소(화면 1,000+ 파일) 전수 분석 → 93KB + 96KB 아키텍처 문서, 인수인계 문서 1종으로 업무 인계 가능한 체계 구축
- 레거시(Java 7 + Ant + Oracle) 3층 구조 복원·기동, PostgreSQL 전용 요소 29곳+의 Oracle 포팅 호환성 전수 감사
