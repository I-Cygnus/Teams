## Case 1. OOM의 범인은 스택 트레이스 맨 위에 없었다 `엔코아 실무`

**문제 (정량)** — 920만 행 컬럼 분석 작업이 JVM OOM으로 사망. 재현 환경 없음, 현장 접근 제한. 증거는 모니터를 찍은 사진 2장과, 스택 최상단 Producer를 범인으로 지목한 초기 분석서 1부.

**위화감** — RMI idle 스레드와 HttpClient 셀렉터 스레드도 같은 시각에 OOM으로 죽어 있었다. 메모리를 거의 쓰지 않는 유휴 스레드가 죽었다는 것은, 힙 전체가 이미 고갈된 상태에서 아주 작은 할당조차 거절당했다는 뜻이다.

**가설 분기**
1. **Producer 문자열 연결이 원인 (초기 분석)** → 기각. 스택 맨 위는 "마지막으로 요청한 자"이지 "점유한 자"가 아니다. 유휴 스레드 동시 사망을 설명하지 못함
2. **힙을 장기 점유하는 컴포넌트가 따로 있다** → 채택. 질문을 "누가 마지막에 호출됐나"에서 "누가 힙을 점유했나"로 전환

**추적** — Consumer의 결과 적재 경로에서 `if (DATA_SAVE_CNT == 0 || ...)` 발견. 설정이 누락되면 0이고, 0이면 무제한 적재. git blame으로 이력을 따라가니 과거 "결과 미적재 버그"를 수정하면서 한도를 함께 풀어버린 회귀 커밋이 특정됐다.

**조치** — ① 모든 설정 경우(미설정·0·오입력)에 결과 버퍼 ≤ 100건 보장 ② `-Xmx` 상한 + OOM 시 힙덤프 자동 확보 ③ "0=무제한" 시맨틱 자체를 제거.

**측정** — 결과 버퍼: 무제한 → 100건 이하 상시 보장. 동일 조건 재실행 검증 통과.

**배움** — 발생 지점과 원인 지점은 다르다. 그리고 "0=무제한" 같은 매직 값은 설정 누락을 곧바로 장애로 만든다.

> 전체 과정: 블로그 「OOM의 범인은 스택 트레이스 맨 위에 없었다」

## Case 2. 커넥션 풀 크기를 수요에서 계산하다 `엔코아 실무`

**문제** — Case 1 수정 후 2차 증상으로 커넥션 타임아웃 발생.

**대안 비교**
1. **풀 크기 증설** → 기각. 왜 부족한지 모르는 채 늘리면 다음 규모에서 재발. 수요 구조를 모른 채 공급만 키우는 대응
2. **타임아웃 연장** → 기각. 증상 은폐. 병목은 그대로
3. **수요 모델에서 풀 크기를 역산** → 채택. 스레드 모델을 따라가면 작업당 필요 커넥션은 결정적으로 계산 가능

**진단** — 공급은 N(설정값), 수요는 2N+2(작업 스레드당 2 + 관리용 2). 공급이 수요의 절반이라 고갈은 구조적 필연이었다.

**구현** — ① 수요 기반 산정식으로 풀 크기를 2N+2에 상시 일치 ② 총량이 (2N+2)×M으로 폭증하는 문제에 거버넌스 3계층: 작업당 병렬수 상한 → 동시 작업 수 상한 → DB 계정 CONNECTION LIMIT.

**자체 반증 시도** — 구현 후 적대적 재검토에서 심각 결함 1건을 추가로 발견했다. Manager에서 clamp한 병렬수를 자식 프로세스가 DB 재조회(`COALESCE`)로 우회해 스레드와 풀이 다시 어긋나는 문제. 값이 흐르는 전 구간(Manager → CLI 인자 → 매퍼 → 핸들러)을 추적해 막았다. 배포 직후에는 내가 쓴 폴백 코드의 결함(설정 0이 100이 아닌 1로 폴백)을 "정확히 1건"이라는 증상에서 역추적해 자체 수정했다.

**측정** — 메타 DB 커넥션 총량: 무제한 → 최악 시나리오에서도 상수 72 (수학적 보장).

**배움** — 리소스 한도는 수요에서 계산하고, 통제는 입력에 건다. 그리고 방금 고친 코드가 다음 버그의 1순위 용의자다.

## Case 3. 300GB인데 유실은 없다 — 스캔 없이 내린 확정 판정 `엔코아 실무`

**문제 (정량)** — 프로파일링 상세 테이블 300GB, 요약 테이블 22MB. "데이터가 날아갔다"는 의심이 먼저 나온 상황.

**제약** — 운영 DB. 300GB 테이블 전체 스캔은 서비스 영향 때문에 불가.

**대안 비교**
1. **전체 스캔으로 실측** → 기각. 운영 부하
2. **`pgstattuple` 정밀 측정** → 기각. 역시 전체 읽기 발생
3. **시스템 카탈로그 메타데이터만으로 판정** → 채택. 정확도 손실이 판단에 영향을 주지 않는 수준임을 먼저 검증

**추적 (3단계)** — ① `pg_stat_user_tables`: dead=0인데 live는 31만 행뿐 — 행당 1MB라는 말이 안 되는 밀도 ② heap/TOAST/index 분해: heap이 거의 전부 ③ 결정타 — `pg_class.relpages` 3,662만 페이지 vs rows 31만 = 페이지당 0.009행. **테이블을 읽지 않고 "99.9%가 빈 페이지"를 확정.** 요약 40,082건은 온전했고, 상세는 요약 없는 고아 1건뿐 — 디스크풀 크래시의 잔해. 유실이 아니라 부풀림(bloat).

**조치와 재발 방지** — DELETE + VACUUM FULL로 300GB 회수. 같은 지표(사용 용량·비율·낭비공간)를 상시 조회하는 [테이블 운영 지표] 화면·API를 직접 개발해 "사고 후 사후 진단"을 "화면에서 상시 관측"으로 바꿈.

**배움** — 운영 환경의 진단은 정확도가 아니라 "판단에 충분한 정확도"가 기준이다.

## Case 4. 인증 트래픽의 90%를 백엔드에 도달하기 전에 끊다 `I-Poten`

**문제 (정량)** — SPA 라우팅마다 인증 상태 조회 API가 호출돼 동일 검증이 반복(~200ms). 인증 코드가 컨트롤러 71곳에 복사되어 있었고, 그 복사본들 사이에 버그가 숨어 있었다.

**대안 비교**
1. **클라이언트 캐싱** → 기각. 토큰 상태를 JS가 다루면 XSS 노출면 확대
2. **토큰 TTL 단축 + Refresh 재설계** → 보류. 효과는 있으나 일정 대비 큰 수술이라 후순위 분리
3. **Nginx 앞단 차단** → 채택. HttpOnly 쿠키는 JavaScript가 못 읽지만, Nginx는 읽을 수 있다

**구현** — ① 인증을 Interceptor + 커스텀 어노테이션 + ArgumentResolver 파이프라인으로 일원화 — 컨트롤러 인증 코드 71곳 → 0곳 ② 상태 확인 요청은 Nginx가 쿠키 존재만 보고 단축 응답 — 백엔드 미도달.

**보안 경계 명시** — 이 최적화는 비-인가 보조 경로(상태 힌트)에 한정한다. 보호 리소스 접근은 여전히 애플리케이션 계층에서 Redis 세션을 검증한다. 만료 토큰이 단축 응답을 받아도 이후 API에서 401로 걸러진다.

**측정** — 인증 트래픽 90% 감소(동접 100명 × 10페이지 기준 1,000회 중 900회 앞단 처리), 응답 ~200ms → 1ms 미만, 인증 상태 조회 평균 2ms.

**배움** — 중복은 지우는 게 아니라 구조로 흡수한다. 그리고 계층마다 볼 수 있는 정보가 다르다는 것 자체가 설계 재료다.

## Case 5. RAM 3.7GiB에서 컨테이너 5개 살리기 `I-Poten 인프라`

**문제 (정량)** — t3.medium 단일 EC2(RAM 3.7GiB)에 Spring Boot + FastAPI + Nginx + MySQL + Redis 공존. 스왑 861MiB 사용 중, 배포 순간 메모리 요구 6.4GiB+로 스왑 폭주.

**원인 2개 특정** — ① Spring Boot 컨테이너에 `-Xmx` 미적용: docker-compose의 `command`가 Dockerfile `ENTRYPOINT`를 통째로 덮어써 JVM 옵션이 사라져 있었다(JVM이 RAM 1/4 ≈ 900MiB 자동 점유) ② 프론트 빌드가 EC2 위에서 `--max-old-space-size=4096`으로 실행 — 총 RAM 초과.

**대안 비교 (빌드 이전)**
1. **GHCR push → EC2 pull** → 채택. 백엔드와 동일 패턴, Nginx 설정 유지, 태그 교체 롤백
2. **산출물 S3 → rsync** → 기각. 볼륨 재설계 + 8개 디렉터리 동기화 로직 필요
3. **S3 + CloudFront 직접 호스팅** → 중장기 보류. Nginx의 MFE 라우팅·레이트리밋·인증 단축 경로를 전부 엣지로 이관해야 함

**구현** — `exec java $JAVA_OPTS`로 PID 1 정상화 + `-Xms256m -Xmx512m -XX:+UseG1GC -XX:+ExitOnOutOfMemoryError -XX:+HeapDumpOnOutOfMemoryError` (OOM 시 좀비 대신 즉사·재시작·증거 확보). 빌드는 GitHub Actions 러너(RAM 7GiB)로 이전, `platforms: linux/amd64` 명시로 ARM 이미지 사고 원천 차단, GHA 캐시로 재빌드 5~10분 단축.

**측정** — Spring 피크 900~1200MiB → 600MiB. 배포 순간 총 사용량 6.4GiB+ → 2.1~2.9GiB. 빌드 시 EC2 점유 4GiB → 0.

**배움** — 클라우드 비용 최적화의 첫걸음은 스케일업이 아니라, 지금 자원이 어디로 새는지 정확히 아는 것.

## Case 6. 화면의 58%가 거짓일 수 있다 — OKR 진척률 버그 `I-Fence`

**문제** — 진척률 공식이 `current / target × 100` — 시작값을 0으로 가정. "이탈률 8% → 5%" 같은 감소형 목표는 표현 자체가 불가능했다. 현재 7%(실제 진척 33%)가 화면에는 **140%**로 표시됐다.

**판단** — 기능 부족이 아니라 버그다. 대시보드가 보여주는 숫자의 절반 이상이 틀릴 수 있는 상태에서, 화면을 늘리는 것보다 숫자를 바로잡는 게 먼저다.

**구현** — baseline(시작값) 필드 도입 + KrType 4종(METRIC_UP / METRIC_DOWN / MILESTONE / PERCENT)별 진척률 계산 분기. 초과 달성은 100으로 clamp — 120%는 잘한 게 아니라 목표가 쉬웠다는 뜻이므로, 원값은 `rawProgress()`로 분리 제공. 숫자보다 사람이 먼저 아는 위험 신호는 Confidence(ON_TRACK/AT_RISK/OFF_TRACK)로 별도 입력. 마이그레이션 SQL은 멱등하게(120줄).

**배움** — 지표 시스템에서 최악의 버그는 죽는 버그가 아니라, 그럴듯한 거짓 숫자를 계속 보여주는 버그다.
