# 팀 블로그 글쓰기 스타일 가이드

> 시골쥐 × 서울쥐 Engineering Blog의 **모든 글이 공유하는 스타일**을 정리한 문서입니다.
> 새 글을 쓰거나(사람이든 AI든) 기존 글을 다듬을 때, 이 문서를 기준으로 삼으면 톤·구조·표기·디자인이 자동으로 일관됩니다.
> 근거가 된 글: `choi/01`(Spring Security), `choi/02`(Claude 패턴), `min/01`(Term 도메인), `min/02`(TSV 적재), `common/*`(팀 공용 4편).

---

## 0. 한눈에 보는 핵심 원칙

이 블로그의 글은 전부 다음 6가지를 공유합니다. 나머지는 이걸 구체화한 것입니다.

1. **"기능 소개"가 아니라 "판단의 근거"를 쓴다.** 무엇을 만들었는지가 아니라 *왜 그렇게 결정했는지*가 본문의 중심.
2. **존댓말 + 1인칭 회고체.** 독자에게 말을 거는 `합니다/입니다`체, 글쓴이는 `저/저희`.
3. **정직하게 트레이드오프와 한계를 스스로 밝힌다.** "이게 정답"이 아니라 "지금 이 맥락에서 최선".
4. **정량적 근거로 말한다.** 퍼센트·응답시간·건수·Before/After 비교표.
5. **구조가 반복된다.** 도입 훅 → `Part N` 심화 → 전체 조망 → `마치며`. 각 파트는 `hr`로 분리.
6. **겸손하게 닫는다.** 배운 점 + 다음 계획 + 감사/피드백 요청.

## 1. 데이터 모델 — 글은 `BlogPost` 객체다

글은 마크다운 파일이 아니라 **TypeScript 객체**(`src/data.ts`의 `BlogPost`)입니다. 한 글 = 한 `.ts` 파일(`src/blog/<package>/NN-slug.ts`).

```ts
export interface BlogPost {
  id: string;                 // 패키지 내 고유 id (보통 '1','2' 또는 'kebab-slug')
  package: BlogPackage;       // 'choi' | 'common' | 'min'
  title: string;              // 질문형/역발상형 제목 선호 (§2.1)
  excerpt: string;            // 2~3문장 요약. "무엇을 + 어떤 수치/결과로 + 무엇을 공유"
  category: BlogCategory;     // 'Frontend'|'Backend'|'Design'|'Product'|'Culture'
  authorId?: MemberId;        // 팀원 글이면 id로 연결 (common에서 사용)
  authorOverride?: {          // 외부/필명 저자면 직접 명시 (choi/min에서 사용)
    name: string; role: string; accent: string;   // accent = 저자 대표색(hex)
  };
  publishedAt: string;        // 'YYYY-MM-DD'
  readingMinutes: number;     // 실제 분량에 맞춰 (에세이 5~10, 심화 12~18)
  cover: string;              // CSS linear-gradient 문자열 (이미지 없을 때 폴백)
  coverImage?: string;        // 실제 썸네일 이미지 경로 '/blog/<pkg>/NN/xxx.png'
  tags: string[];             // 기술 키워드 3~5개 ('Spring Boot','Auth',...)
  body: BlogBlock[];          // 본문 = 블록 배열 (§6)
}
```

### 본문 블록 타입 (`BlogBlock`)

| type | 용도 | 필드 |
|---|---|---|
| `p` | 문단 | `text` (인라인 `**bold**` / `` `code` `` / `*italic*` 가능) |
| `h2` | Part 제목 | `text` |
| `h3` | Part 내부 소주제 | `text` |
| `list` | 나열(요구사항·장점·체크리스트) | `items: string[]` |
| `code` | 코드/다이어그램/흐름 | `language`, `text` |
| `table` | 비교·트레이드오프 | `headers: string[]`, `rows: string[][]` |
| `quote` | 핵심 인사이트 한 줄 | `text` |
| `image` | 개념 설명 이미지 | `src`, `alt`, `caption?` |
| `hr` | Part 구분선 | (없음) |

> `excerpt` 예시(그대로 참고): "Spring Security 대신 5개 클래스로 인증을 직접 만들고, Nginx 설정 몇 줄로 인증 트래픽의 90%를 줄인 여정. I-Poten 백엔드 인증 아키텍처를 공유합니다."

## 2. 글의 거시 구조 (뼈대)

모든 심화 글은 아래 순서를 따릅니다. 이 뼈대만 지켜도 "우리 블로그 글"처럼 읽힙니다.

```
1. 도입 훅         (hr 없음, p 여러 개 + 필요시 list)
   ─ 공감 질문 or 흔한 선택 제시
   ─ 이번 프로젝트의 맥락/요구사항
   ─ "그래서 결론부터 말씀드리면 …" 로 결론 선공개
── hr ──
2. Part 1 (h2)     ─ h3 소주제들 + code/table/list
── hr ──
3. Part 2, 3 … (h2)
── hr ──
4. 전체 조망       (Part 없이) "전체 아키텍처 한눈에 보기" / 비교표
── hr ──
5. 원칙 문장 절    "결국 핵심은 …" — 글 전체를 관통하는 한 문장
── hr ──
6. 마치며 — 부제   배운 점 + 남은 과제/다음 글 예고 + 감사
```

### 2.1 제목 (`title`)

- **질문형/역발상형을 선호.** 통념에 질문을 던진다.
  - "Spring Security, 정말 필요할까?"
  - "Term은 단어 테이블이 아니라 기준 데이터다"
- **명사 단정형도 가능.** "…으로 바라보기", "…에서 배운 것".
- 마케팅 카피·과장(🚀, "완벽한", "혁신적") 금지.

### 2.2 도입 훅 (첫 3~5문단)

세 가지 오프닝 중 하나로 시작합니다.

1. **독자에게 던지는 질문** — "여러분은 로그인 기능을 만들 때 어떤 선택을 하시나요?" / "여러분은 '용어 사전' 기능을 만든다면 어떤 테이블부터 떠올리시나요?"
2. **흔한 선택 → 의문** — "대부분 Spring Security를 도입합니다. 저도 처음엔 그랬습니다. 그런데 …"
3. **맥락 선언** — "I-Poten은 IT 개발자 취업 준비생을 위한 … 서비스입니다."

이어서 **요구사항/제약을 `list`로 정리**하고, **"그래서 결론부터 말씀드리면 …"**로 결과(수치 포함)를 먼저 공개합니다. 결말을 숨기지 않습니다.

### 2.3 Part 제목 (`h2`)

- `Part N. 소제목` 형식. 소제목은 **주장이 담긴 서술형**이 기본.
  - "Part 1. 5개 클래스로 만든 인증 파이프라인"
  - "Part 3. 인증 트래픽의 90%는 필요 없었다"
  - "Part 5. 하지만 Runner 방식에는 한계가 있다"
- 전체 조망/원칙/마무리 절은 `Part` 번호를 떼고 의미형 제목: "전체 아키텍처 한눈에 보기", "결국 핵심은 \"지금 이 맥락에서 최선인가\"", "마치며 — …".

### 2.4 마무리 (`마치며 — 부제`)

- 제목은 항상 **`마치며 — <한 줄 요약>`** (em dash).
  - "마치며 — 아직 배울 게 많습니다"
  - "마치며 — Term은 단어 저장소가 아니다"
- 구성: ① 글 전체를 **한 문장으로 요약한 `quote`** → ② 배운 점 → ③ 남은 과제/다음 글 예고 → ④ 감사·피드백 요청.
  - "부족한 글 읽어주셔서 감사합니다. 더 좋은 아이디어나 피드백은 언제든 환영합니다."

## 3. 문장·문법 스타일 (톤앤매너)

### 3.1 종결 어미
- **`합니다/입니다`체(존댓말)** 통일. 반말·개조식 금지(단, `list`/`table` 내부는 명사·개조식 허용).
- 독자를 향한 표현을 적극 사용: `~하시나요?`, `~해보겠습니다`, `~하죠`, `~거예요/했어요`(가끔, 대화감).
- 수사 의문문으로 문제를 제기하고 다음 문단에서 답한다.

### 3.2 인칭·주어
- 글쓴이 1인칭: **`저`/`저는`/`저도`**. 팀 주체는 **`저희`/`우리`**.
- 독자 호칭: **`여러분`** (주로 오프닝 질문에서).

### 3.3 강조·리듬
- **정량화로 말한다.** "인증 트래픽의 90%", "~200ms → <1ms", "4줄이 1줄이 되었습니다", "1,000회 중 900회를 Nginx에서 차단".
- **대비 구조.** Before/After, 현재/전환 시점, 기존/개선.
- **em dash(—)** 로 부연·전환·삽입. "각 호출마다: 쿠키 파싱 → Redis 조회 → DB 조회 = ~200ms".
- **짧은 확정 문장으로 리듬을 끊는다.** "이게 전부입니다.", "즉시 무효화.", "어노테이션 하나면 끝이죠."

### 3.4 정직성 (이 블로그의 정체성)
- **트레이드오프를 반드시 명시한다.** 별도 절/표로: "트레이드오프도 인지하고 있습니다", 현재 vs 전환 시점 표.
- **한계를 스스로 밝힌다.** "이 최적화의 한계도 압니다", "하지만 분리는 끝이 아니라 시작이다".
- 과장·단정 대신 조건부 표현: "…라고 생각합니다", "…일 수 있습니다", "상황에 따라 다릅니다".

## 4. 수사 전략 (전개 방법)

한 Part(또는 h3) 안에서 자주 쓰는 전개 패턴:

- **문제 → 인사이트 → 해결 → 검증 → 한계.**
  예) 과도한 토큰 검증 트래픽(문제) → "HttpOnly 쿠키는 JS는 못 읽지만 Nginx는 읽는다"(인사이트, `quote`) → Nginx 설정(해결, `code`) → Before/After 표(검증) → "이 최적화의 한계도 압니다"(한계).
- **결정의 근거 중심.** 코드는 주장을 뒷받침하는 보조 자료. "왜 category를 문자열로 넣지 않았나", "N:M을 직접 풀어낸 이유"처럼 **왜(why)**를 h3 제목으로.
- **실무 맥락으로 구체화.** 추상 원칙을 항상 I-Poten 사례로 착지시킨다.
- **협업/성장 서사(특히 min).** "팀 리더가 이 부분을 짚어주었습니다 … 협업의 중요성을 느꼈습니다."
- **원칙 문장으로 승화.** 글 끝에서 개별 사례를 일반 원칙으로: "기술 선택은 '이게 좋은가 나쁜가'가 아니라 '지금 이 맥락에서 최선인가'의 문제입니다."

## 5. 마크다운·인라인 표기 규칙

`p`, `list`, `table` 셀의 `text`에서 사용할 수 있는 인라인 표기:

| 표기 | 의미 | 예 |
|---|---|---|
| `**굵게**` | **결론·핵심 주장·강조 문장**. 문단당 1개 안팎, 남발 금지 | "**Spring Security 대신 5개 클래스로 전체 인증을 직접 만들었습니다.**" |
| `` `코드` `` | 식별자·클래스·파일·API·설정키 | `` `TermService.register()` ``, `` `CommandLineRunner` ``, `` `.md` `` |
| `*이탤릭*` | 비유·강조 어구 | "*한 명에게 풀스택 + 인프라 + 디자인을 동시에 시키는 셈*" |

- 굵게는 **"이 글에서 기억할 한 문장"**에 집중해서 사용. 문단마다 굵게가 있으면 강조가 죽습니다.
- 코드 식별자는 반드시 백틱. 본문에서 `Term`, `@LoginUser`, `chunk`처럼.

## 6. 블록별 사용 규칙

### `p` — 문단
- 한 문단 = 한 생각. 3~4문장이면 끊는다. 첫 문단은 렌더링 시 리드(21px)로 커지므로 **훅 문장**을 배치.

### `h2` / `h3`
- `h2` = Part 경계(§2.3). 앞에 반드시 `hr`.
- `h3` = Part 내부 소주제. 서술형 제목 선호("인터셉터 하나가 모든 인증을 처리한다"), 번호형도 가능("1. 애플리케이션 실행과 데이터 적재 책임이 섞인다").

### `list` — 나열
- 용도: 요구사항, 장점, 체크리스트, takeaway, 실패 케이스.
- 항목 앞에 **`**키워드** — 설명`** 패턴을 자주 씀:
  - "**완성 즉시 작성한다.** 시간이 지나면 설계 의도가 휘발됩니다."
- 개조식·명사형 허용. 3~7개 권장.

### `code` — 코드·다이어그램·흐름
- 실제 코드뿐 아니라 **흐름/파이프라인/디렉토리 트리/아키텍처 박스**도 `language:'text'`로 표현(§7).
- 코드는 요점만. 전체 클래스보다 **핵심 메서드/설정 몇 줄** + 한글 주석.

### `table` — 비교
- 트레이드오프/Before·After/개념 대조에 사용. 첫 열은 항목명(굵게 렌더됨).
- 예: `['항목','Before','After','개선률']`, `['구분','카테고리','태그']`, `['담는 것','담지 않는 것']`.

### `quote` — 핵심 인사이트
- **글의 캐치프레이즈 한 줄**에만. 글당 1~수 개.
- 위치: 파트의 결론 또는 `마치며` 직전(전체 요약).
- 예: "HttpOnly 쿠키는 JavaScript가 못 읽지만, Nginx는 읽을 수 있다.", "도구는 갈아끼울 수 있지만, 그 도구를 다루는 작업 방식은 자산으로 남습니다."

### `image`
- 개념 설명/증빙 이미지. **`alt` 필수**, `caption`은 보조 설명일 때만.
- 경로 규칙: `public/blog/<package>/<NN>/<name>.png` → `src: '/blog/<package>/<NN>/<name>.png'`.
- 렌더링 시 본문보다 넓게(뷰포트 기준) 표시되므로 가로형 이미지가 잘 어울림.

### `hr`
- **오직 Part 경계**에만. 문단 사이 장식용으로 쓰지 않는다.

## 7. 코드블록 컨벤션

- 사용 `language`: `java`, `tsx`, `sql`, `nginx`, `bash`, `text`, `markdown`.
- **한글 주석**, 단계에는 번호 주석:
  ```java
  // 1. @PublicEndpoint → 검증 없이 통과
  // 2. HttpOnly 쿠키에서 userToken 추출
  ```
- **Before/After**는 한 블록 안에서 주석으로 라벨: `// Before: …`, `// After: …`.
- `text`로 표현하는 4종 다이어그램:
  - **흐름(화살표):** `TSV 파일 준비\n→ 로컬 DB 적재\n→ SQL dump …`
  - **디렉토리 트리:** `docs/\n├── PROJECT.md\n└── modules/`
  - **아키텍처 박스:** `┌────────┐ │ Layer 1 │ └────────┘`
  - **관계도:** `Term ── ManyToOne ── TermCategory`
- 렌더러는 코드블록을 **다크 테마 + 언어 라벨 + 복사 버튼**으로 보여줍니다. 그러니 코드는 복사해서 바로 읽히도록 자기완결적으로.
- ⚠️ **트레일링 공백 주의.** 일부 기존 `min` 글의 `text` 코드에 줄 끝 공백이 다수 있습니다(`min/01`, `min/02`). 새 글에서는 넣지 마세요.

## 8. 작성자·패키지별 목소리

톤의 큰 틀은 공유하되, 저자별 결이 다릅니다.

### `choi` — Mr.Choi (accent `#0EA5E9`)
- **확신에 찬 대화체.** 통념에 역발상("정말 필요할까?"), 강한 주장을 굵게로 못 박음.
- 짧고 리듬감 있는 문장, "~했어요"도 섞음. 트레이드오프·정량 근거를 특히 강조.
- 실전 아키텍처(인증/트래픽 최적화)와 "지금 이 맥락에서 최선인가" 류 원칙.
- `choi/02`는 예외적으로 도입부에서 **역사/개념(총·균·쇠 비유, AI 발전사 이미지, 벤치마크 표)**로 크게 빌드업 후 실전 패턴으로 좁혀 들어감.

### `min` (accent `#10B981` / 글마다 다름 `#3B82F6`)
- **차분한 회고·설명체.** 교과서적으로 단계를 밟고, 결정의 이유를 꼼꼼히.
- **협업·피드백·배움**을 서사로 넣음("팀 리더가 짚어주었다", "협업의 중요성을 느꼈습니다").
- 겸손·담백. 마지막에 "다음 단계" 목록으로 확장 방향 제시.

### `common` — 팀 공용 (`authorId`로 연결)
- **짧은 에세이(5~10분).** `Design`/`Product`/`Culture`/`Frontend` 등 주제 다양.
- 원칙/규칙 나열형이 많음("우리의 3가지 규칙", "4가지 의식"). 코드보다 관점 중심.
- 심화 글의 무거운 `Part N` 골격 대신, `h2` 몇 개 + `list` + 마무리 `quote`의 가벼운 구조.

## 9. 디자인·렌더링 (독자가 보는 형태)

글을 쓸 때 이 렌더링을 전제로 하면 결과물이 예쁘게 나옵니다. (`src/blog/ui.tsx`, `src/pages/BlogDetail.tsx`, `src/index.css`)

- **색 토큰(`.blog`):** bg `#f6f7f9`, 본문 잉크 `#16181d`, accent 인디고 `#4c6ef5`. 카테고리 틴트 — Frontend 인디고, Backend 블루, Design 핑크, Product 오렌지, Culture 그린. **색은 포인트로만**(무지개 금지).
- **폰트:** Pretendard. 제목(`.display`) 자간 `-0.025em`. 본문 16~17px/줄높이 1.85, 첫 문단 리드 21px.
- **썸네일(`Cover`):** 기본은 뉴트럴 카드(제목+카테고리 라벨+좌측 3px 카테고리 엣지). `coverImage`가 있으면 **사진 풀블리드 + 하단 다크 스크림 + 흰색 제목**.
- **상세 페이지:** 우측 **스크롤스파이 목차(TOC)**, **다크 코드블록(복사 버튼)**, **뷰포트보다 넓은 이미지**, 읽기 진행바, 저자 카드, "이어서 읽기".
- **저자 표기:** 팀원은 `authorId`(→ `teamMembers`에서 이름/역할/브리프), 외부·필명은 `authorOverride`(`name`/`role`/`accent`). `accent`는 저자 대표색.
- **커버 그라데이션(`cover`)** 은 이미지가 없을 때만 쓰이는 폴백이지만, 항상 저자 accent 계열로 채워 둡니다.

## 10. 새 글 작성 체크리스트

- [ ] 제목이 질문형/역발상형이고 과장이 없다.
- [ ] `excerpt`가 "무엇을 + 어떤 수치/결과로 + 무엇을 공유"를 2~3문장에 담았다.
- [ ] 도입 훅(질문/흔한 선택/맥락) 후 **결론을 먼저 공개**했다.
- [ ] 본문이 `Part N`(h2) + `hr` 경계로 나뉘고, 각 Part에 h3 소주제가 있다.
- [ ] **트레이드오프/한계를 밝히는 절**이 최소 1개 있다.
- [ ] 주장마다 **정량 근거(수치·표·Before/After)**가 붙는다.
- [ ] 굵게는 핵심 문장에만, 식별자는 전부 백틱.
- [ ] 코드블록에 `language`가 있고 주석이 한글이며 트레일링 공백이 없다.
- [ ] `quote`가 글의 캐치프레이즈 한 줄로 쓰였다.
- [ ] `마치며 — <요약>`에 배운 점 + 다음 계획 + 감사/피드백이 있다.
- [ ] `tags` 3~5개, `category`·`readingMinutes`·`publishedAt` 정확.
- [ ] 썸네일: `coverImage` 넣을 경우 `public/blog/<pkg>/<NN>/`에 파일 배치.
