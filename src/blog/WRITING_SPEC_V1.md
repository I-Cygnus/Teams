# 블로그 글쓰기 표준 명세 V1 (최종)

> **이 문서의 목적**: 시골쥐×서울쥐 Engineering Blog의 글을 쓸 때, **어떤 AI·어떤 모델·어떤 사람이 쓰더라도 동일한 구조와 동일한 품질**이 나오도록 하는 결정론적 명세.
> 기반: ① 기존 블로그 스타일(`STYLE_GUIDE.md` — "판단의 근거" 중심) + ② 우아한테크코스 10분 테코톡 분석(`uploads/테코톡-스타일-분석.md` — "비유로 가르치기" 중심)을 합친 최종본.
> **사용법**: 이 문서 전체 + 원본 자료(주제 소스)를 함께 주고 "이 명세대로 글을 써라"라고 지시한다. 이 문서에 없는 것은 하지 않는다.

---

## 0. 핵심 정체성 — 두 스타일의 합

이 블로그의 글은 아래 한 문장으로 정의된다.

> **"테코톡처럼 가르치고, 우리 블로그처럼 정직하게 판단을 남긴다."**

| 축 | 테코톡에서 가져온 것 | 기존 블로그에서 가져온 것 |
|---|---|---|
| 구조 | 비유 하나로 관통, 왜→무엇→어떻게→어디에 사다리 | Part N + hr 구분, 도입 훅, 마치며 |
| 표현 | 비유 → 실물 2단 착지, 개념 다이어그램 | 정량 수치(Before/After), 코드 근거 |
| 정직성 | 생략 선언 + 학습 로드맵 | 트레이드오프·한계 명시, "지금 이 맥락에서 최선" |
| 착지 | 실무 적용으로 끝맺기 | I-Poten 실제 사례·실제 선택 |

이 4개 축이 전부 들어가야 완성된 글이다. 하나라도 빠지면 미완성.

## 1. 데이터 모델 — 글은 TypeScript 객체다

글은 마크다운 파일이 아니라 `src/blog/<package>/NN-slug.ts`의 **`BlogPost` 객체**로 작성한다.

```ts
export interface BlogPost {
  id: string;                 // 패키지 내 고유 번호 문자열 ('1','2',...)
  package: 'choi' | 'common' | 'min';
  title: string;              // §3 제목 규칙
  excerpt: string;            // 2~3문장: 무엇을 + 어떤 방식/수치로 + 무엇을 공유
  category: 'Frontend' | 'Backend' | 'Design' | 'Product' | 'Culture';
  authorOverride?: { name: string; role: string; accent: string };
  publishedAt: string;        // 'YYYY-MM-DD'
  readingMinutes: number;     // 개념 강의형 12~14, 판단 기록형 14~20
  cover: string;              // 저자 accent 계열 linear-gradient (이미지 폴백)
  coverImage?: string;        // '/blog/<pkg>/NN/xxx.png' (있을 때만)
  tags: string[];             // 기술 키워드 3~5개
  body: BlogBlock[];          // 본문 블록 배열
}
```

본문 블록 타입과 각 용도:

| type | 용도 | 규칙 |
|---|---|---|
| `p` | 문단 | 한 문단 = 한 생각, 3~4문장. 인라인 `**굵게**`, `` `코드` ``, `*이탤릭*` 가능 |
| `h2` | Part 제목 | 앞에 반드시 `hr`. `Part N. 제목` 형식 |
| `h3` | Part 내 소주제 | 서술형 제목 ("세션의 강점 — 즉시 통제권") |
| `list` | 나열 | `**키워드** — 설명` 패턴. 3~7개 |
| `code` | 코드·다이어그램 | `language` 필수. 다이어그램은 `language:'text'`. 한글 주석. 트레일링 공백 금지 |
| `table` | 비교·수렴 | 첫 열은 항목명. 비교형 글의 필수 요소 |
| `quote` | 핵심 인사이트 한 줄 | 글당 1~3개. 파트의 결론 또는 마치며 직전 |
| `image` | 개념 이미지 | `alt` 필수. 경로 `/blog/<pkg>/NN/<name>.png` |
| `hr` | Part 경계 | 오직 Part 경계에만 |

**주의**: `text` 필드에 `${...}` 리터럴이 필요하면(예: `.env`의 `${DB_PASSWORD}`) 그 문단은 **큰따옴표 문자열**로 감싼다. 작은따옴표+템플릿 조합은 TS 문법 오류를 낸다.

## 2. 글 유형 결정 — 첫 번째 분기

글을 쓰기 전에 원본 자료를 보고 **딱 하나의 유형**을 고른다. 판단 기준은 기계적으로:

```
원본 자료에 "우리가 실제로 겪은 사건·수치·결정"이 중심인가?
├── YES → [A] 판단 기록형   (예: choi/01 Spring Security, choi/04 Docker 판단기록)
└── NO, 개념·지식 전달이 중심인가?
    └── YES → [B] 개념 강의형 (예: choi/05 쿠키vs세션vs토큰, choi/06 Docker 아파트)
```

- **[A] 판단 기록형**: 1인칭 사건 서사가 척추. 결론 선공개. 정량 Before/After가 주인공.
- **[B] 개념 강의형**: 앵커 비유가 척추. 사다리식 전개(결론을 쌓아서 도달). 마지막에 실물(자사 사례) 착지.

이 명세의 나머지는 **[B] 개념 강의형을 기본**으로 서술하고, [A]와 다른 지점만 표시한다. (이 문서가 "합친 최종 버전"인 이유: [B]의 뼈대 안에 [A]의 정직성·정량·실사례를 필수 요소로 심었기 때문.)

## 3. 제목 규칙

**공식**: `핵심 개념(명사형) + [선택] 부제(— 질문 또는 비유 예고)`

- 앞부분은 테코톡식 **검색 가능한 명사형** — 글이 무엇을 다루는지 0.5초 안에 판별되게.
- 부제는 우리 블로그식 **질문형/비유 예고** — 관점을 담는다.
- 예 (실제 채택작):
  - `쿠키 vs 세션 vs 토큰 — 서버는 나를 어떻게 기억하는가`
  - `Docker는 왜 VM보다 가벼울까 — 아파트로 이해하는 컨테이너`
- [A] 판단 기록형은 질문/역발상 단독 허용: `Spring Security, 정말 필요할까?`
- **금지**: 🚀 이모지, "완벽 정리", "총정리", "혁신", 클릭베이트 수식어.

## 4. 앵커 비유 — 글의 척추 (개념 강의형 필수)

### 4.1 규칙

1. **비유는 반드시 1개.** 여러 비유를 흩뿌리지 않는다. 하나의 비유가 도입부터 마치며까지 관통한다.
2. 비유는 **개념의 모든 하위 요소를 매핑**할 수 있어야 채택한다. 매핑 표를 먼저 만들어 검증하고, 3개 이상 매핑이 안 되면 비유를 버리고 다시 고른다.
3. 마치며에서 **비유로 되돌아와 전체를 한 문단으로 요약**한다 (수미상관).

### 4.2 검증된 매핑 예시 (이 수준을 기준으로 삼는다)

**쿠키vs세션vs토큰 = 단골 카페:**

| 개념 | 비유 |
|---|---|
| HTTP 무상태 | 기억력 없는 사장님 |
| 쿠키 | 손님이 들고 다니는 쪽지 |
| 세션 | 카운터의 장부 + 번호표 |
| 토큰 | 사장님 서명이 든 위조 불가 카드 |
| 토큰 무효화 불가 | 발급한 카드를 회수할 방법이 없음 |

**Docker = 아파트 단지:**

| 개념 | 비유 |
|---|---|
| 이미지 / 컨테이너 | 모델하우스 / 입주한 집 |
| VM vs 컨테이너 | 단독주택(자기 보일러) vs 아파트 세대(중앙설비 공유) |
| 커널 | 건물 중앙 설비 + 관리사무소 |
| namespace / cgroups | 세대 간 벽 / 세대별 사용량 상한 |
| 레이어 | 골조→배관→인테리어 공정 |
| Compose / 프록시 | 단지 / 경비실(유일한 정문) |

### 4.3 비유 → 실물 2단 착지 (필수)

비유로 직관을 만든 뒤에는 **반드시 개발자가 이미 아는 실제 소프트웨어/코드/수치**로 검증한다. 비유로만 끝나는 절은 금지.

```
[비유]  "크롬은 탭마다 다른 회의실을 쓴다"
[실물]  → "그래서 탭 하나가 죽어도 다른 탭은 산다. IE는 그렇지 않았다"
```

실물 착지의 우선순위: ① 자사(I-Poten) 실제 사례 ② 유명 소프트웨어(크롬, 유튜브, Redis) ③ 실제 코드/설정 ④ 정량 수치.

## 5. 글의 거시 구조 — 고정 골격

블록 순서는 아래 골격을 **그대로** 따른다. Part 수는 4~6개.

```
① 도입 훅 (p 3~4개, hr 없음)
   - 첫 문단: "기원 서사" — 문제/모순 제시 ("HTTP는 아무것도 기억하지 못합니다")
   - 둘째 문단: 그 문제가 독자 일상과 연결됨을 보임
   - 셋째 문단: 이 글이 무엇을 어떤 방식으로 다루는지 + **앵커 비유 예고** ("비유는 단골 카페입니다")
   - [A형만] "결론부터 말씀드리면 …" 결론 선공개 추가
── hr ──
② Part 1 ~ N (h2 + h3 + p/code/table/list)
   - 각 Part: 비유 확장 → 개념 정의 → 원리 → 실물 착지
   - 전개 순서는 §6의 주제 형태별 구조를 따름
   - 강점/약점이 있는 개념은 h3로 "강점 — …" / "약점 — …" 쌍 구성
── hr ──
③ 수렴 Part (비교형이면 필수): 전체를 하나의 table로 모으고 quote로 한 문장 결론
── hr ──
④ 실물 착지 Part: "그래서 우리(I-Poten)는 무엇을 골랐나"
   - 실제 선택 + 그 이유 + 정직한 트레이드오프 ("~을 포기하고 ~을 샀다")
   - "지금 이 맥락에서 최선" 원칙으로 마무리
── hr ──
⑤ "오늘 다루지 않은 것들" (생략 선언 + 로드맵, list 3~4개)
   - 각 항목: **주제** — 왜 생략했고 언제 필요한지 한 줄
── hr ──
⑥ 마치며 — <한 줄 요약> (em dash 필수)
   - quote: 글 전체를 관통하는 한 문장 (층위 구분 또는 원칙)
   - p: 앵커 비유로 되돌아와 전체 요약 (수미상관)
   - p: 감사 + 피드백 요청 ("부족한 글 읽어주셔서 감사합니다. 피드백은 언제든 환영합니다.")
```

## 6. 주제 형태별 전개 구조 — 두 번째 분기

Part 내부의 전개 순서는 주제의 형태가 결정한다. 아래 표에서 기계적으로 매칭:

| 주제 형태 | 판별 | 구조 | 예 |
|---|---|---|---|
| **비교형** | "A vs B" 대조가 핵심 | A 단독 설명 → B 단독 설명 → (C 단독) → **vs 표로 수렴** | 쿠키vs세션vs토큰, Process vs Thread |
| **매트릭스형** | 독립된 두 축이 있음 | 축(판별 기준) 2개를 먼저 정의 → 2×2 조합 순회 | Blocking/Non-Blocking × Sync/Async |
| **파이프라인형** | 입력→출력 과정 | 시간 순서를 목차로, 공정 라인처럼 | 브라우저 렌더링, 빌드→배포 |
| **연대기형** | 버전/세대가 있음 | 각 버전의 한계가 다음 버전의 등장 이유 (문제-해결 연쇄) | HTTP/0.9→3, 인증의 역사 |
| **계층형** | 층이 쌓여 있음 | 하위→상위 상향식. "이전 층만으로 안 되는 문제 → 다음 층" | OSI, 메모리 계층 |
| **심화 사다리형** | 단일 개념 깊이 파기 | 정의 → 성질 → 문제 상황 → 해결책 | 트랜잭션→ACID→이상현상→격리레벨 |

비교형 수렴 표 바로 아래에는 반드시 `quote`로 **선택의 본질을 한 문장**으로: *"결국 ~할 것인가(A), ~할 것인가(B)의 선택입니다."*

## 7. 문장·톤 규칙

1. **합니다/입니다체** 통일. 가끔 `~죠`, `~거죠`로 대화감. 반말 금지 (list/table 내부는 개조식 허용).
2. 글쓴이 1인칭 `저/저희`, 독자 호칭 `여러분`(오프닝에서만).
3. **수사 의문문으로 문제 제기 → 다음 문단에서 답한다.** ("그럼 뭘 실어 나르면 될까요? 여기서 두 갈래 길이 나옵니다.")
4. **짧은 확정 문장으로 리듬을 끊는다.** ("진실은 항상 카운터에 있습니다.", "'37번'.")
5. **em dash(—)** 로 부연·전환. 괄호 남발 금지.
6. `**굵게**`는 "이 글에서 기억할 문장"에만 — 문단당 최대 1개. 식별자·설정키·파일명은 전부 `` `백틱` ``.
7. 조건부 표현으로 겸손 유지: "~라고 생각합니다", "~일 수 있습니다". 단정·과장 금지.
8. **정량 수치를 최소 2곳 이상** 배치 (예: "780MB → 330MB", "3분 → 15초", "90% 차단").

## 8. 다이어그램 규칙

- 모든 글에 `language:'text'` 다이어그램 **2~4개** 필수. 유형은 4가지 중 선택: 구조도 / 흐름도(화살표) / 비교 배치도(좌우 대비) / 상태·요청 시퀀스.
- 박스 문자(`┌─┐│└┘`)와 화살표(`→ ▶ ▼`)로 그린다. 각 줄 끝 트레일링 공백 금지.
- 다이어그램 안에도 비유 라벨을 함께: `proxy (경비실) ← 단지의 유일한 정문`.
- 코드 블록은 실제 동작 코드 요점만 + **한글 주석**. Before/After는 한 블록에서 `# 나쁨:` / `# 좋음:` 주석 대비.

## 9. 작성 절차 — 순서대로 실행하는 알고리즘

어떤 AI든 아래 순서를 그대로 밟는다. 순서를 바꾸지 않는다.

```
STEP 1  원본 자료를 읽고 [A]판단기록 / [B]개념강의 유형 결정 (§2)
STEP 2  주제 형태 결정 (§6 표에서 매칭) → Part 목차 초안 (4~6개)
STEP 3  앵커 비유 선정 → 매핑 표 작성 → 하위 개념 3개 이상 매핑 검증 (§4)
        실패 시 비유 재선정. 성공한 매핑 표가 곧 글의 설계도.
STEP 4  각 Part에 "실물 착지" 소재 배정 (자사 사례 > 유명 SW > 코드 > 수치)
STEP 5  "오늘 다루지 않은 것들" 목록 확정 (3~4개) — 무엇을 버릴지 먼저 결정
STEP 6  §5 골격에 맞춰 본문 집필 (도입 훅 → Part → 수렴 → 착지 → 생략 → 마치며)
STEP 7  quote 배치 확인 (수렴 표 아래 1개 + 마치며 1개, 총 1~3개)
STEP 8  §11 체크리스트로 전수 검증 → 미충족 항목 수정
STEP 9  BlogPost 객체로 변환, index.ts 등록, npx tsc -b 통과 확인
```

## 11. 최종 검증 체크리스트 (전 항목 통과해야 완성)

**구조**
- [ ] 제목: 명사형 + 부제(질문/비유), 클릭베이트 없음
- [ ] 도입 3~4문단: 기원 서사 → 독자 연결 → 비유 예고
- [ ] Part 4~6개, 모든 `h2` 앞에 `hr`
- [ ] 주제 형태(§6)에 맞는 전개 구조 사용
- [ ] 비교형이면 수렴 table + 직후 quote 존재
- [ ] "그래서 우리는 무엇을 골랐나" 실물 착지 Part 존재
- [ ] "오늘 다루지 않은 것들" 절 존재 (3~4개, 각각 이유 포함)
- [ ] 마치며: quote + 비유 수미상관 + 감사 인사

**표현**
- [ ] 앵커 비유 1개가 도입~마치며 관통, 매핑 3개 이상
- [ ] 모든 비유 뒤에 실물 착지 (비유로만 끝나는 절 없음)
- [ ] 정량 수치 2곳 이상
- [ ] `text` 다이어그램 2~4개 (트레일링 공백 없음)
- [ ] quote 총 1~3개
- [ ] 굵게는 문단당 최대 1개, 식별자는 전부 백틱
- [ ] 합니다체 통일, 수사 의문문 → 답 패턴 사용

**정직성**
- [ ] 각 선택지의 강점과 약점이 모두 서술됨 (한쪽 찬양 금지)
- [ ] 자사 선택의 트레이드오프 명시 ("~을 포기하고 ~을 샀다")
- [ ] 생략한 범위를 숨기지 않고 선언

**기술**
- [ ] `BlogPost` 객체 문법 유효 (`${}` 리터럴은 큰따옴표 문자열)
- [ ] `src/blog/<pkg>/index.ts`에 import + 배열 등록
- [ ] `npx tsc -b` 통과

## 12. 금지 목록 (안티패턴)

1. **비유 없이 정의부터 나열** — 백과사전이지 블로그 글이 아니다.
2. **비유 여러 개 혼용** — 앵커가 흔들리면 글 전체가 흩어진다.
3. **비유로만 끝나는 설명** — 반드시 실물로 착지.
4. **"완전 정리"식 목차** — 전부 다루려는 순간 아무것도 전달 못 한다. 버릴 것을 먼저 정하고 생략을 선언하라.
5. **결론 없는 비교** — vs 표를 그렸으면 "그래서 우리는"이 따라와야 한다.
6. **수치 없는 주장** — "빨라졌다"가 아니라 "3분 → 15초".
7. **트레이드오프 없는 추천** — 모든 선택은 대가를 명시한다.
8. **이모지·과장 수식어·마케팅 톤** — 🚀, "완벽한", "게임체인저" 금지.
9. **hr을 장식용으로 사용** — Part 경계 외 금지.
10. **첫 문단에 결론 대신 인사말** — "안녕하세요, 오늘은 ~에 대해 알아보겠습니다" 금지. 첫 문장부터 문제/모순으로 진입.
